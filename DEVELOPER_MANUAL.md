# Uptight Developer Manual

This manual provides information for developers working with the Uptight codebase.

## 1. Introduction

Uptight is a code for empirical tight binding (ETB) calculations, primarily developed at the University of Rome Tor Vergata. It implements ETB methods based on foundational papers by Slater & Koster (1954), Jancu et al. (1998), and Tan et al. (2016).

The code is often used as a library linked into other simulation software, notably TiberCAD, but can also be used standalone or via the provided `PARAMETERIZER` tool.

**Key Features:**
*   Empirical Tight Binding calculations for various materials (III-V, III-nitrides, Si, Ge, 2D materials).
*   Fortran-based library (`uptight.a`).
*   Integration capabilities with external simulation tools.
*   Parameterization support.

## 2. Codebase Overview

This section provides a high-level view of the project's directory structure.

*   **`src/`**: Contains the main source code.
    *   **`src/lib_uptight/`**: The core Fortran library implementation for tight-binding calculations. This is the main part of the code.
    *   **`src/configure` / `src/configure.ac`**: Autotools configuration script and its source file. Used to check dependencies and generate `make.common`.
    *   **`src/make.common`**: Shared makefile definitions, generated by `configure`.
    *   **`src/api/`**: Application Programming Interface (API) code. Contains Fortran source (`upt_api.f90`, `uptightAPICommon.f90`) and C/C++ header files (`uptight.h`, `fortran.h`, `Upt*.h`) defining an API for calling Uptight routines from other languages (primarily C/C++). Includes test programs (`test_upt_api_c.c`, `test_upt_api_f.f90`) and potentially specific bindings for TiberCAD (`tiber_test/`).
    *   **`src/cf_rot/`**: Contains code related to rotations (`rota.f90`), possibly for crystal field or coordinate transformations.
    *   **`src/davidson/`**: Implementation of the Davidson iterative algorithm (`davidson*.f*`, `eigensolver_davidson.f90`), a method for finding eigenvalues/eigenvectors of large sparse matrices, common in electronic structure calculations.
    *   **`src/palloc/`**: Utility modules for memory allocation (`allocation.f90`), precision control (`precision.f90`), error handling (`errors.f90`), and I/O (`input_output.f90`).
*   **`parameters/`**: Contains various sets of empirical tight-binding parameters for different materials and models (e.g., `sp3`, `sp3s`).
*   **`bulk/`**: Contains input data files (`*.data`, `*.etb`) defining bulk crystal structures and parameters for specific materials (e.g., `GaAs.data`, `Si.data`).
*   **`TEST/`**: Contains test cases, example input files (`*.in`, `*.dat`), scripts (`*.script`), and expected output data for verifying the code's functionality across different scenarios (e.g., bulk GaAs, GaN quantum dots).
*   **`lib_arpack/`**: Contains pre-compiled versions of the ARPACK library (`libarpack.a`), which provides routines for large-scale eigenvalue problems. This is an optional dependency.

## 3. Building the Code

*(Details adapted from README.md)*

### Dependencies
*   Fortran Compiler (gfortran or ifort)
*   `make`
*   BLAS and LAPACK libraries (`libblas-dev`, `liblapack-dev`)
*   Optional: ARPACK (`libarpack-dev`)
*   Optional: MPI (`libopenmpi-dev`, `openmpi-bin`)

### Build Steps
1.  **Configure:** Run `./src/configure` from the project root. This generates `src/make.common` and other configuration files based on your system.
2.  **Build Library:** Navigate to `src/lib_uptight/` and run `make uptight.a`. This compiles the core Fortran files and creates the static library `uptight.a`.
3.  **Build Example Tool (Optional):** In `src/lib_uptight/`, run `make PARAMETERIZER`. This links `uptight.a` with necessary routines to create the `PARAMETERIZER` executable.

### Build System Internals

The build process relies on Autoconf for configuration and Make for compilation and linking.

*   **Configuration (`./src/configure`):**
    *   Uses `src/configure.ac` as input.
    *   Detects Fortran, C, and C++ compilers.
    *   Checks for required libraries (BLAS, LAPACK) and optional ones (ARPACK, MPI, MKL, CUDA).
    *   Generates `src/make.common`, which stores the detected compiler paths, flags (e.g., `FC`, `FFLAGS`, `LDFLAGS`), and library paths/flags (`LIBMKLIB`, `LIBCUDA`, `LIBMPI`).

*   **Compilation (`src/lib_uptight/Makefile`):**
    *   Includes `../make.common` to inherit the configuration settings.
    *   Includes `Makefile.dep` at the end, which contains automatically generated dependencies between source files (`.f90`, `.F90`) and object files (`.o`) to ensure correct recompilation order when source files change.
    *   Defines the list of core Fortran source files (`SOURCES`, `SOURCES2`).
    *   Uses Fortran Preprocessor Flags (`FPPFLAGS`) to embed version information (from `git describe`) and compilation date into the code.
    *   Handles conditional compilation based on configuration options (e.g., `-DUPT_MPI` if MPI is enabled via `ifdef UPT_MPI`).
    *   Compiles `.f90` source files directly using the Fortran compiler (`$(FC)`) and flags (`$(FFLAGS)`).
    *   Preprocesses `.F90` files using the C preprocessor (`$(CPP)`) with `$(FPPFLAGS)` before compiling them with the Fortran compiler. This allows using C-style macros and includes within Fortran code.
    *   The primary target `uptight.a` compiles all source files listed in `SOURCES` and `SOURCES2` into object files (`.o`) and then archives them into a static library using `ar cq`.
    *   The `PARAMETERIZER` target compiles `parameterizer.f90` and links it along with `f_exceptions.o` and all objects in `uptight.a` (`$(OBJECTS)`) against the required libraries (BLAS, LAPACK, etc., specified in `$(LIBMKLIB)` and potentially others like `$(LIBARPACK)`, `$(LIBCUDA)`).

## 4. Core Library (`src/lib_uptight/`) - Detailed Documentation

This section provides detailed documentation for the modules and routines within the `src/lib_uptight/` directory, structured for easy lookup. The subsections below correspond to the main functional categories identified from the source files listed in the `src/lib_uptight/Makefile`.

### 4.1 Fundamental Definitions & Globals

This subsection details modules that define fundamental parameters, constants, and precision settings used globally across the library.

#### 4.1.1 `precision.f90` (Module `precision`)

*   **Purpose:** Establishes the numerical precision for floating-point calculations and provides functions for comparing real numbers within a specified tolerance.
*   **Parameters:**
    *   `sp` (INTEGER, PARAMETER): Kind parameter for single precision reals, obtained using `selected_real_kind(6, 30)`.
    *   `dp` (INTEGER, PARAMETER): Kind parameter for double precision reals, obtained using `selected_real_kind(14, 100)`. This is the primary precision used for most calculations (`REAL(dp)`).
    *   `qp` (INTEGER, PARAMETER): Kind parameter for quadruple precision reals, obtained using `selected_real_kind(28, 300)`. Usage is likely limited or experimental.
    *   `EPS` (REAL(dp), PARAMETER): A small constant value (1.d-10), potentially used as a threshold for zero checks.
    *   `PREC` (REAL(dp), PARAMETER): A precision constant (1.0d-04).
    *   `ACCUR` (REAL(dp), PARAMETER): An accuracy constant (1.0d-06).
    *   `emach` (REAL(dp)): Module variable storing the calculated machine accuracy.
    *   `fuzzy` (LOGICAL, PARAMETER): Flag set to `.TRUE.`, indicating that comparisons using `equiv` should likely use relative tolerance by default.
*   **Subroutines/Functions:**
    *   `set_machine_acc()`: Calculates machine epsilon using `dlamch()` and stores it in the module variable `emach`. Called once at initialization.
    *   `dlamch()` (REAL(dp) FUNCTION): Computes machine epsilon for double precision. It iteratively halves a value until `1.0 + value == 1.0`, then doubles it. *Note: This might be an internal implementation or rely on an external LAPACK `dlamch` function depending on linking.*
    *   `equiv` (INTERFACE): Generic interface for comparing numerical values.
        *   `equiv_val(a, b, deviation, fuzzy)` (LOGICAL FUNCTION): Compares two scalars `a` and `b` (REAL(dp)).
            *   **Inputs:** `a`, `b` (values), `deviation` (tolerance threshold), `fuzzy` (logical flag).
            *   **Logic:** If `a` and `b` are both close to zero (within `emach`), returns `.TRUE.`. If `fuzzy` is `.TRUE.`, checks if the relative difference `ABS(a-b) / MIN(ABS(a), ABS(b))` is less than `deviation / 100.0`. If `fuzzy` is `.FALSE.`, checks if the absolute difference `ABS(a-b)` is less than or equal to `deviation`.
            *   **Output:** `.TRUE.` if `a` and `b` are considered equivalent within the specified tolerance, `.FALSE.` otherwise.
        *   `equiv_vec(a, b, deviation, fuzzy)` (LOGICAL FUNCTION, DIMENSION(:)): Compares a REAL(dp) vector `a` element-wise against a REAL(dp) scalar `b` using the same logic as `equiv_val`.
            *   **Inputs:** `a` (vector), `b` (scalar), `deviation`, `fuzzy`.
            *   **Output:** A logical array of the same size as `a`, where each element indicates if the corresponding element `a(i)` is equivalent to `b`.

#### 4.1.2 `globals.f90` (Module `globals`)

*   **Purpose:** Defines globally accessible integer parameters that serve as standard indices for atomic orbital states and two-center coupling types. This provides a consistent naming convention across different modules.
*   **Parameters (Orbital Indices):** Defines integer parameters mapping standard orbital names to indices 1 through 10.
    *   `s = 1`, `px = 2`, `py = 3`, `pz = 4`, `se = 5` (for s*), `dxy = 6`, `dyz = 7`, `dzx = 8`, `dx2y2 = 9`, `dz2r2 = 10`.
    *   `n_ref_states` (INTEGER, PARAMETER): Set to 10, the total number of reference orbital states defined.
*   **Parameters (Coupling Indices):** Defines integer parameters mapping standard two-center integral (coupling) types to indices 1 through 21.
    *   `sss = 1`, `sps = 2`, `pss = 3`, `pps = 4`, `ppp = 5`, `seses = 6` (s*s*s), `sess = 7` (s*ss), `sses = 8` (ss*s), `seps = 9` (s*ps), `pses = 10` (ps*s), `sds = 11`, `dss = 12`, `pds = 13`, `dps = 14`, `pdp = 15`, `dpp = 16`, `seds = 17` (s*ds), `dses = 18` (ds*s), `dds = 19`, `ddp = 20`, `ddd = 21`.
    *   `n_ref_couplings` (INTEGER, PARAMETER): Set to 21, the total number of reference coupling types defined.
    *   `n_intra` (INTEGER, PARAMETER): Set to 7, the number of intra-atomic coupling types relevant for the Tan parameterization scheme.
*   **Other Parameters:**
    *   `LST = 500`, `MST = 200`, `SST = 100`: Integer parameters likely defining standard lengths for character strings used for file paths (Long), medium strings, and short strings, respectively.

#### 4.1.3 `constants.f90` (Module `constants`)

*   **Purpose:** Defines fundamental physical constants and conversion factors used in the calculations, mostly related to atomic units.
*   **Parameters:**
    *   `eovh` (REAL(dp), PARAMETER): A conversion factor, value `1.0581818181818181E-003`. The units are unclear from the name alone (possibly Angstroms per Hartree?).
    *   `pi` (REAL(dp), PARAMETER): Mathematical constant pi (3.1415926535897932_dp).
    *   `HAR` (REAL(dp), PARAMETER): Hartree energy unit converted to electron volts (27.2113845_dp eV).
    *   `ATU` (REAL(dp), PARAMETER): Atomic unit of length (Bohr radius, a0) converted to Angstroms (0.529177249_dp Angstrom).
    *   `Kb` (REAL(dp), PARAMETER): Boltzmann constant in atomic units (Hartree / Kelvin) (3.16681558E-06_dp Hartree/K).
    *   `j` (COMPLEX(dp), PARAMETER): The imaginary unit, defined as `cmplx(0.d0, 1.d0, dp)`.
    *   `max_ind_D` (INTEGER, PARAMETER): A large integer constant (100000), possibly used as a default maximum dimension for dynamically allocated arrays or as an index limit.

### 4.2 Core Data Structures

This section details the primary derived types (structures) used to organize data within the `lib_uptight` library.

#### 4.2.1 `type_defs.f90`

*   **Purpose:** Defines the main derived data types (structures) used to represent the physical system (atoms, basis, materials) and the tight-binding parameters.
*   **Constants:**
    *   `ATOMLEN`, `TYPELEN`, `CPLLEN`, `STATELEN`: Integer parameters defining standard character lengths for atom names (2), type strings (2, maybe intended to be larger?), coupling names (5), and state names (5).
    *   `MAX_NUM_NEIGHBOURS`: Maximum number of neighbors stored per atom (24).
    *   `hydrosat`: Character parameter defining the symbol for passivating Hydrogen ('Hx').
*   **Key Derived Types:**
    *   `ion_basis`: Represents the collection of atoms in the simulation cell.
        *   `n_basis` (INTEGER): Number of actual atoms (excluding passivation).
        *   `n_dg_bond` (INTEGER): Number of dangling bonds (passivating atoms).
        *   `atomtypes` (CHARACTER(TYPELEN), POINTER, DIMENSION(:)): Array of unique atom type names (e.g., 'Ga', 'As', 'Hx').
        *   `coord` (REAL(dp), POINTER, DIMENSION(:,:)): Coordinates of all atoms (including passivating ones) in fractional units of primitive vectors. Shape: `(3, n_basis + n_dg_bond)`.
        *   `dg_coord` (REAL(dp), POINTER, DIMENSION(:,:)): Coordinates of dangling bond sites. Shape: `(3, n_dg_bond)`.
        *   `strain` (REAL(dp), POINTER, DIMENSION(:,:)): Local strain tensor `(xx, yy, zz)` for each atom. Shape: `(3, n_basis + n_dg_bond)`.
        *   `mat` (INTEGER, POINTER, DIMENSION(:)): Material index for each atom.
        *   `ion` (INTEGER, POINTER, DIMENSION(:)): Ion index (within the material's ion list) for each atom.
        *   `type` (INTEGER, POINTER, DIMENSION(:)): Atom type index (referencing `atomtypes`) for each atom.
        *   `n_dg` (INTEGER, POINTER, DIMENSION(:)): Number of dangling bonds for each atom.
        *   `n_st` (INTEGER, POINTER, DIMENSION(:)): Number of orbitals (basis functions) for each atom.
        *   `valence` (INTEGER, POINTER, DIMENSION(:)): Valence electrons for each atom.
        *   `periodic` (LOGICAL): True if periodic boundary conditions are used.
        *   `periodic_BC` (CHARACTER(3)): String indicating periodic directions ('xyz', 'xy', 'no', etc.).
        *   `start` (REAL(dp), POINTER, DIMENSION(3)): Origin offset of the simulation cell.
        *   `prim` (REAL(dp), POINTER, DIMENSION(3,3)): Primitive lattice vectors (columns) in Angstrom.
        *   `rec_latt` (REAL(dp), POINTER, DIMENSION(3,3)): Reciprocal lattice vectors (columns) in 1/Angstrom.
    *   `ion_orbit`: Defines parameters for a specific type of ion within a material or parent material.
        *   `energy` (REAL(dp), POINTER, DIMENSION(:)): Array of onsite energies for each orbital state. Size matches the number of states for this ion type.
        *   `so_energy` (REAL(dp), POINTER, DIMENSION(:)): Array of spin-orbit coupling energies (e.g., Delta_p, Delta_d).
        *   `state` (CHARACTER(STATELEN), POINTER, DIMENSION(:)): Array of orbital names (e.g., 's', 'px'). Size matches the number of states.
        *   `so_state` (CHARACTER(1), POINTER, DIMENSION(:)): Array of orbital names relevant for spin-orbit coupling (e.g., 'p', 'd').
        *   `deg` (INTEGER, POINTER, DIMENSION(:)): Degeneracy of each distinct orbital energy entry read from the input file (e.g., 3 for 'p').
        *   `ind_ref` (INTEGER, POINTER, DIMENSION(:)): Map from this ion's orbital index (1 to `n_st`) to the global reference orbital index (1 to `n_ref_states`).
        *   `ind_ref_inv` (INTEGER, POINTER, DIMENSION(:)): Inverse map of `ind_ref`. Shape `(n_ref_states)`.
        *   `offset` (REAL(dp)): Energy offset applied to this ion type (e.g., for band alignment).
        *   `b_d` (REAL(dp)): Parameter related to d-orbital strain effects (Jancu scheme).
        *   `name` (CHARACTER(TYPELEN)): Name of the ion (e.g., 'Ga').
        *   `valence` (INTEGER): Valence electrons.
        *   `content` (REAL(dp)): Concentration (relevant in alloys, usually 1.0 for pure parent).
    *   `pair_coupling`: Defines parameters for interactions between a pair of ion types.
        *   `cpl` (CHARACTER(CPLLEN), POINTER, DIMENSION(:)): Array of coupling type names (e.g., 'sss', 'sps'). Size `n_ref_cpl` after sorting.
        *   `ons_corr`, `so_corr`, `intra` (CHARACTER(CPLLEN), POINTER, DIMENSION(:)): Names for onsite, SO, and intra-atomic correction types (Tan scheme).
        *   `energy` (REAL(dp), POINTER, DIMENSION(:)): Array of two-center integral values corresponding to `cpl`. Size `n_ref_cpl` after sorting.
        *   `scaling` (REAL(dp), POINTER, DIMENSION(:)): Array of distance-scaling exponents corresponding to `cpl`. Size `n_ref_cpl` after sorting.
        *   `fac_P`, `fac_S`, `fac_Q` (REAL(dp), POINTER, DIMENSION(:)): Parameters for dipole/quadrupole corrections (Tan scheme). Size `n_ref_cpl` after sorting.
        *   `fac_I`, `l_I` (REAL(dp), POINTER, DIMENSION(:)): Parameters for onsite correction (Tan scheme). Size depends on number of orbital types read.
        *   `fac_so` (REAL(dp), POINTER, DIMENSION(:)): Parameters for SO correction (Tan scheme). Size depends on number of SO states read.
        *   `fac_C` (REAL(dp), POINTER, DIMENSION(:)): Parameters for intra-atomic coupling (Tan scheme). Size depends on number of intra terms read.
        *   `fac_O` (REAL(dp)): Parameter for offset correction (Tan scheme).
        *   `l_O` (REAL(dp)): Length scale for offset correction (Tan scheme).
        *   `dist_ref` (REAL(dp)): Reference bond distance for the parameters.
        *   `delta_d` (REAL(dp)): Bond distance correction (Tan scheme).
        *   `name` (CHARACTER(ATOMLEN), DIMENSION(2)): Names of the two ions in the pair (e.g., 'Ga', 'As').
        *   `order` (INTEGER): Interaction order (e.g., 1 for 1st NN, 2 for 2nd NN).
    *   `parent_data`: Defines a constituent material used to build an alloy.
        *   `n_ion` (INTEGER), `ion` (TYPE(ion_orbit), POINTER, DIMENSION(:)): Number and list of ion types in the parent.
        *   `n_pair` (INTEGER), `pair` (TYPE(pair_coupling), POINTER, DIMENSION(:)): Number and list of pair couplings in the parent.
        *   `content` (REAL(dp)): Concentration of this parent in the alloy.
        *   `lat_par` (REAL(dp), DIMENSION(3)): Lattice parameters (a, b, c) of the parent.
        *   `ref_axis` (REAL(dp), DIMENSION(3)): Reference crystallographic axis used for parameterization (e.g., [001] for ZB, [111] for WZ).
        *   `u_par` (REAL(dp)): Internal displacement parameter (e.g., for WZ).
        *   `int_str_par` (REAL(dp)): Internal strain parameter.
        *   `e_v` (REAL(dp)): Valence band maximum energy (used for alignment).
        *   `data_file` (CHARACTER(100)): Name of the file containing these parameters.
        *   `name` (CHARACTER(20)), `type` (CHARACTER(20)), `cry` (CHARACTER(20)): Name, type (simple, binary), and crystal structure of the parent.
        *   `scheme` (CHARACTER(10)): Parameterization scheme ('jancu', 'tan').
    *   `material_data`: Defines a material in the simulation, which could be a pure crystal or an alloy.
        *   `nr_parents` (INTEGER, POINTER, DIMENSION(:)): Number of parent materials (1 for pure, >1 for alloy). Size depends on context (e.g., size 1 for base materials, size 2 for interfaces).
        *   `parent` (TYPE(parent_data), POINTER, DIMENSION(:)): Array of `parent_data` types.
        *   `ion` (TYPE(ion_orbit), POINTER, DIMENSION(:)): Array of `ion_orbit` types (potentially averaged for VCA alloys).
        *   `bowing` (REAL(dp), POINTER, DIMENSION(:)): Bowing parameters for alloy interpolation.
        *   `gap_corr` (REAL(dp), DIMENSION(2)): Band gap correction parameters.
        *   `lat_par` (REAL(dp), DIMENSION(3)), `u_par` (REAL(dp)), `int_str_par` (REAL(dp)): (Potentially averaged) lattice parameters for the material.
        *   `ref_axis` (REAL(dp), DIMENSION(3)): Reference axis.
        *   `max_order` (INTEGER): Maximum interaction order needed for this material.
        *   `cry` (CHARACTER(20)), `type` (CHARACTER(20)), `name` (CHARACTER(20)), `scheme` (CHARACTER(10)): Crystal structure, type, name, and scheme.
        *   `alloy` (LOGICAL), `alloy_random` (LOGICAL), `extra_cpl` (LOGICAL), `average_cat` (LOGICAL): Flags indicating alloy type and properties.
    *   `TStructure`: Holds data read directly from the geometry input file (`.upg`).
        *   `gen_filename` (CHARACTER(MST)): Name of the input geometry file.
        *   `n_atoms` (INTEGER): Total number of atomic sites read from file (including potential passivation atoms).
        *   `C_S` (CHARACTER(1)): Character indicating coordinate type ('C'artesian or 'S'caled/Direct).
        *   `nr_atomtypes` (INTEGER): Number of unique atom symbols found.
        *   `atomtypes` (CHARACTER(TYPELEN), POINTER, DIMENSION(:)): Array of unique atom type names.
        *   `n_danglings` (INTEGER): Count of passivation atoms found.
        *   `hydro_type` (INTEGER): Index in `atomtypes` corresponding to the passivation atom symbol (`hydrosat`).
        *   `coord` (REAL(dp), POINTER, DIMENSION(:,:)): Raw coordinates read from file. Shape `(3, n_atoms)`.
        *   `nn_list` (INTEGER, POINTER, DIMENSION(:,:)): Neighbor list read from file (if present). Shape `(MAX_NUM_NEIGHBOURS, n_atoms)`.
        *   `mat` (INTEGER, POINTER, DIMENSION(:)): Material index for each site read from file.
        *   `atomtype` (INTEGER, POINTER, DIMENSION(:)): Atom type index for each site read from file.
        *   `indexa`, `inv_indexa` (INTEGER, POINTER, DIMENSION(:)): Index maps used for reordering atoms (moving H to the end).
        *   `start` (REAL(dp), DIMENSION(3)): Origin offset read from file (if `C_S`='S').
        *   `prim` (REAL(dp), DIMENSION(3,3)): Primitive lattice vectors read from file (if `C_S`='S').
*   **Key Subroutines/Functions:**
    *   `create_basis`, `allocate_mat_ion`, `allocate_parent_ion`, `allocate_ion`, `allocate_parent_pair`, `allocate_pair`, `allocate_ons_corr`, `allocate_so_corr`, `allocate_intra`: Allocation routines for the derived types and their pointer members. Check for allocation errors.
    *   `destroy_material`, `destroy_basis`, `nullify_basis`, `nullify_ion`, `destroy_structure`, `nullify_structure`: Deallocation and nullification routines for safe memory management.
    *   `write_basis`, `write_materials`, `write_ion_orbits`, `write_ion_couplings`: Output routines for printing the contents of these data structures, useful for debugging.

#### 4.2.2 `listtypes.f90`

*   **Purpose:** Defines simple derived types used for creating linked lists. These are primarily internal helper types used by other modules (like `lists.f90` and `TB_ham.f90`).
*   **Key Derived Types:**
    *   `cplxs`, `ints`, `dprec`, `names`: Basic list nodes containing a single data element (`nbr` or `name`) of complex, integer, double precision, or character type, respectively, and a pointer (`next`) to the subsequent node in the list.
    *   `matrix`: List node containing a pointer to a 2D complex matrix (`mat`) and a `next` pointer. Used in `TB_ham.f90` for temporary storage of Hamiltonian blocks before assembling the sparse matrix.
    *   `v_pointer`: List node containing a pointer to a 1D complex vector (`p`) and a `next` pointer.

#### 4.2.3 `upt_param.f90`

*   **Purpose:** Defines the central derived type `OUPT` which aggregates almost all parameters and data structures required for an Uptight calculation. This acts as the main "context" object passed between high-level routines in the `uptight.F90` module and example programs.
*   **Key Derived Type:**
    *   `OUPT`: Contains members for:
        *   **Control & Environment:** `verbose` (INTEGER), `mpi_comm` (INTEGER).
        *   **File Paths:** `gen_filename`, `gen_out`, `state_file`, `potential_file`, `database_path`, `work_path`, `out_path`, `load_path`, `out_format` (all CHARACTER).
        *   **Core Data Structures:** `structure` (TYPE(TStructure)), `basis` (TYPE(ion_basis)), `materials` (TYPE(material_data), POINTER, DIMENSION(:)), `interfaces` (TYPE(material_data), POINTER, DIMENSION(:,:)), `nn_map` (TYPE(nearest_neighbours), POINTER, DIMENSION(:)), `ham` (TYPE(CSR)), `U` (TYPE(CSR)).
        *   **Physical Parameters:** `d_H`, `E_H` (REAL(dp) - Passivation), `n_spin` (INTEGER), `poldir` (INTEGER - Optics), `n_ref_st`, `n_ref_cpl` (INTEGER), `k_point` (REAL(dp), DIMENSION(3)), `c_axis` (REAL(dp), DIMENSION(3)).
        *   **Model Flags:** `d_onsite_shift_flag`, `potential_flag`, `relat`, `scaling`, `syst_rotated`, `ioutput_flag`, `optmat`, `check_bondmap`, `hybrid_passivation` (all LOGICAL).
        *   **Input/Output Data:** `pot_data` (REAL(dp), POINTER, DIMENSION(:)), `eigen_values` (REAL(dp), POINTER, DIMENSION(:)), `eigen_vectors` (COMPLEX(dp), POINTER, DIMENSION(:,:)), `particles` (INTEGER, POINTER, DIMENSION(:)).
        *   **Reference Data:** `ref_states` (CHARACTER(STATELEN), POINTER, DIMENSION(:)), `ref_couplings` (CHARACTER(CPLLEN), POINTER, DIMENSION(:)).
        *   **Solver Parameters:** `num_vb`, `num_cb`, `start_vb`, `start_cb` (INTEGER), `min_iter`, `long_iter`, `max_iter` (INTEGER), `lambda_cb`, `lambda_vb` (REAL(dp)), `fast_tol`, `long_tol`, `ort_tol` (REAL(dp)), `solver_flag` (INTEGER), `dynamic` (LOGICAL), `bitoff` (REAL(dp)), `seed_flag` (LOGICAL).
        *   **Output Control:** `vol_fraction`, `grid_step` (REAL(dp)).
        *   **Performance:** `estimate_factor` (REAL(sp)).
*   **Key Subroutines/Functions:**
    *   `set_defaults(upt)`: Initializes an `OUPT` variable with sensible default parameter values.

### 4.3 Utility Modules

This section covers various utility modules providing common functionalities like memory management, error handling, I/O, timing, vector/matrix operations, sorting, and list handling.

#### 4.3.1 `allocation.f90`

*   **Purpose:** Provides wrapper routines for allocating and deallocating memory, primarily for pointer arrays, while tracking memory usage. This helps in monitoring memory consumption and potentially identifying leaks.
*   **Key Derived Type:**
    *   `mem_log`: Contains `iolog` (file unit for logging), `alloc_mem` (current allocated memory in bytes), and `peak_mem` (maximum memory allocated so far).
*   **Key Subroutines/Functions (Interfaces):**
    *   `log_allocatep`, `log_deallocatep`: Allocate/deallocate **pointer** arrays (1D/2D) of various types (complex(`pz`/`pz2`), double(`pd`/`pd2`), integer(`pi`/`pi2`), character(`pc`)) and update a `mem_log` variable. Checks if pointer is already associated before allocating.
    *   `log_allocate`, `log_deallocate`: Allocate/deallocate **allocatable** arrays (1D-4D) of various types (logical(`l`), complex(`z`/`z2`/`z3`), double(`d`/`d2`/`d3`/`d4`), integer(`i`/`i2`/`i3`), character(`c`)) and update a `mem_log` variable. Checks if array is already allocated.
    *   `resetMemLog(mlog)`: Initializes `alloc_mem` and `peak_mem` in `mlog` to zero.
    *   `openMemLog(iofile, mlog)`: Opens a log file ('memory.log') and associates it with `mlog%iolog`.
    *   `writeMemLog(mlog)`: Writes current memory usage to the log file.
    *   `writeMemInfo(mlog)`: Writes current memory usage (formatted) to the log file unit.
    *   `writePeakInfo(mlog)`: Writes peak memory usage (formatted) to the log file unit.
    *   `closeMemLog(mlog)`: Writes peak usage and closes the log file.
    *   `memstr(mem, dec, str)`: Utility to format memory size `mem` (INTEGER*8) into a string `str` with appropriate units (bytes, kb, Mb, Gb) and scaling factor `dec`.

#### 4.3.2 `errors.f90` & `exceptions.F90` & `f_exceptions.f90` & `exception_codes.h`

*   **Purpose:** Provide a centralized mechanism for handling errors, printing informative messages, and terminating the program execution via `STOP`.
*   **Key Components:**
    *   `exception_codes.h`: (C preprocessor header) Defines integer constants (macros) for various error conditions (e.g., `_ERR_ALLOC_ERR`, `_ERR_HAM_UNPAIR`, `_ERR_INPUT`). These codes provide a standardized way to signal specific errors.
    *   `exceptions.F90`: (Fortran module, preprocessed using `exception_codes.h`) Declares Fortran INTEGER parameters corresponding to the error codes defined in the header file (e.g., `ERR_ALLOC_ERR = _ERR_ALLOC_ERR`). This makes the error codes accessible within Fortran code.
    *   `errors.f90`: Contains subroutines that print detailed, context-specific error messages to standard output based on an `error_type` string and optional file/list names. These routines typically call one of the `throw_*` routines afterwards.
        *   `read_errors(error_type, file, list)`: Handles syntax errors encountered during input file reading (e.g., 'missing', 'not integer', 'bad pairs').
        *   `alloc_error(module_name, routine_name, name)`: Handles memory allocation failures.
        *   `dealloc_error(module_name, routine_name, name)`: Handles memory deallocation failures.
        *   `lattice_errors(error_type, param, value)`: Handles errors related to lattice parameters or neighbor finding.
    *   `f_exceptions.f90`: Contains the core exception-throwing subroutines.
        *   `throw_init_exception(CODE)`: Called for errors during the initialization phase. Prints a generic message based on the integer `CODE` (looked up via SELECT CASE) and then calls `STOP`.
        *   `throw_solve_exception(CODE)`: Called for errors during the solver/calculation phase. Prints a generic message based on `CODE` and calls `STOP`.

#### 4.3.3 `input_output.f90`

*   **Purpose:** Provides utility routines for file handling (opening, finding labels) and formatted input/output conversions.
*   **Key Subroutines/Functions:**
    *   `open_file(file_name, file_num, operation, format_flag, output_flag, replace_flag, stream_flag)`: Opens a file specified by `file_name`.
        *   `operation`: 'read' or 'write'.
        *   `format_flag`: `.TRUE.` for formatted, `.FALSE.` for unformatted.
        *   `output_flag`: `.TRUE.` to print opening message to screen.
        *   `replace_flag`: `.TRUE.` to replace existing file on write, `.FALSE.` to append.
        *   `stream_flag`: `.TRUE.` for stream access (implies unformatted), `.FALSE.` for sequential.
        *   Manages file unit numbers (`file_num`) automatically to avoid conflicts. Includes error checking.
    *   `label_in_file(file_num, label, error, advance)`: Searches for a specific text `label` within an open file `file_num`. Rewinds the file first.
        *   `advance`: Optional character argument. If 'no', the file pointer is left on the same line after the label; otherwise (default), it advances to the next line.
        *   `error`: Logical output, true if the label is not found.
    *   `int_in_file(file_name, file_num, label)`: Reads an integer value associated with a `label` (e.g., finds "label =" and reads the following integer). Includes error handling for missing labels or non-integer values.
    *   `flag_in_file(file_name, file_num, label)`: Reads a logical value associated with a `label` (e.g., finds "label =" and reads the following logical). Includes error handling.
    *   `int_format(i)`: Returns a suitable Fortran format string (e.g., 'i4', 'i6') for printing integer `i` based on its magnitude.
    *   `int_to_char(i)`: Converts an integer `i` to its character string representation.

#### 4.3.4 `clock.f90`

*   **Purpose:** Provides simple routines for timing sections of code using `SYSTEM_CLOCK` (wall time) and `CPU_TIME` (CPU time). Allows for basic nested timing up to `NMAXCLKS` levels.
*   **Key Subroutines/Functions:**
    *   `set_clock()`: Pushes the current wall time onto an internal stack (`t1`). Increments `nclks`.
    *   `write_clock(message)`: Pops the start time (`t1(nclks)`) from the stack, gets the current time (`t2(nclks)`), calculates the difference (handling counter rollover), prints the optional `message` and the elapsed wall time in seconds. Decrements `nclks`.
    *   `get_clock(tm)`: Like `write_clock` but returns the elapsed time in `tm` instead of printing.
    *   `get_sclock()`: Function version of `get_clock`.
    *   `set_time()` / `write_time()`: Similar to `set_clock`/`write_clock` but use `CPU_TIME` for CPU time measurement.
    *   `message_clock(message)`: Prints a `message`, pads with dots for alignment, and calls `set_clock`. Designed to be used with `write_clock` to time and label specific code sections.

#### 4.3.5 `vectors.f90`

*   **Purpose:** Provides basic mathematical operations on vectors (primarily 3D).
*   **Key Subroutines/Functions (Interfaces):**
    *   `norm`: Calculates the Euclidean norm (`sqrt(sum(vec**2))`).
        *   `norm_int(vec)`: For 1D INTEGER vector. Returns REAL(dp).
        *   `norm_real(vec)`: For 1D REAL(sp) vector. Returns REAL(sp).
        *   `norm_dp(vec)`: For 1D REAL(dp) vector. Returns REAL(dp).
        *   `norm_dp_mat(vec)`: For 2D REAL(dp) matrix `vec(:,:)`. Returns a 1D REAL(dp) array containing the norm of each column.
    *   `sort_vec`: Sorts a 1D vector in ascending order. Returns a new sorted vector.
        *   `sort_vec_int(vec)`, `sort_vec_real(vec)`, `sort_vec_dp(vec)`.
    *   `sort_by_norm`: Sorts an array of 3D vectors based on their norm. Returns a new sorted array.
        *   `sort_by_norm_int(vec)`, `sort_by_norm_real(vec)`, `sort_by_norm_dp(vec)`. Input `vec` shape `(3,:)`.
    *   `vec_count`: Counts the number of distinct elements in a 1D vector.
        *   `vec_count_int(vec)`, `vec_count_real(vec)`, `vec_count_dp(vec)`. Uses `equiv` for real comparisons.
    *   `vec_values`: Returns a 1D array containing only the distinct values from an input vector `vec`. Requires the number of distinct values `n_value` as input (obtainable from `vec_count`).
        *   `vec_val_int(vec, n_value)`, `vec_val_real(vec, n_value)`, `vec_val_dp(vec, n_value)`. Uses `equiv` for real comparisons.
    *   `cross_product`: Calculates the cross product of two 3D vectors `vec_a` and `vec_b`.
        *   `cross_product_int`, `cross_product_real`, `cross_product_dp`.
    *   `triple_product`: Calculates the scalar triple product `vec_a . (vec_b x vec_c)`.
        *   `triple_product_int`, `triple_product_real`, `triple_product_dp`.

#### 4.3.6 `sort.f90`

*   **Purpose:** Provides more advanced sorting algorithms, including quicksort and O-sort (a Shell sort variant), often operating indirectly via index arrays or sorting sparse matrix rows.
*   **Key Subroutines/Functions:**
    *   `qsort_index(n, array, indx)`: Sorts a REAL(dp) `array` indirectly by rearranging the INTEGER `indx` array using a quicksort algorithm. The `array` itself is not modified.
    *   `osort_index(length, array, ind)`: Sorts a REAL(dp) `array` indirectly using O-sort (based on diminishing increments related to the golden ratio). Modifies both `array` (locally) and `ind`.
    *   `swap_i(i, j, indx)`, `swap_r(i, j, array)`, `swap_z(i, j, array)`: Utility routines to swap elements `i` and `j` in INTEGER, REAL(dp), and COMPLEX(dp) arrays, respectively.
    *   `sort_csr(n, a, ja, ia, values)`: Sorts the column indices (`ja`) within each row of a CSR matrix defined by `(a, ja, ia)`. If `values` is true, the corresponding matrix elements (`a`) are permuted along with the column indices. Uses `qsort`.
    *   `qsort(a, [b])`: Recursive quicksort implementation. Sorts the INTEGER array `a`. If the optional COMPLEX(dp) array `b` is present, it is permuted in parallel with `a`. Uses `partitionA` or `partitionAB`.
    *   `partitionA(a, marker)`, `partitionAB(a, b, marker)`: Helper routines for `qsort` that partition the array(s) around a pivot element.

#### 4.3.7 `lists.f90`

*   **Purpose:** Implements basic operations (create, add, delete, write) for simple linked lists whose node types are defined in `listtypes.f90`.
*   **Key Subroutines/Functions (Interfaces):**
    *   `create_list(new, start, current)`: Initializes a linked list. Sets `start` and `current` pointers to the `new` node. Implementations for `ints`, `dprec`, `names` node types.
    *   `add_list(new, current)`: Adds a `new` node to the end of the list pointed to by `current`. Updates `current` to point to the new last node. Implementations for `ints`, `dprec`, `names`.
    *   `delete_list(start)`: Deallocates all nodes in a linked list starting from `start`. Nullifies pointers. Implementations for `ints`, `dprec`, `names`.
    *   `write_list(start)`: Prints the contents of a linked list to standard output. Implementations for `ints`, `dprec`, `names`, and also for specific application types `ion_orbit` and `pair_coupling` (likely assumes the list nodes contain pointers to these types).

#### 4.3.8 `matrices.f90`

*   **Purpose:** Contains basic matrix operations (determinant, transpose, inverse) specifically for dense, square, double precision real matrices. These are likely utility functions for small matrices (e.g., 3x3 lattice vectors) rather than the main Hamiltonian.
*   **Key Subroutines/Functions:**
    *   `determinant(mat)`: Recursively calculates the determinant using cofactor expansion. Checks if the matrix is square.
    *   `transp(mat)`: Returns the transpose of the input matrix `mat`.
    *   `inverse(mat)`: Calculates the inverse using the adjugate matrix method (`inverse(A) = adj(A) / det(A)`). Checks if the matrix is square and if the determinant is non-zero. Computationally expensive for large matrices.

#### 4.3.9 `rcm_module.f90`

*   **Purpose:** Implements the Reverse Cuthill-McKee (RCM) algorithm, a graph traversal algorithm used to find a permutation of the nodes (rows/columns) of a sparse matrix that reduces its bandwidth. This reordering can significantly improve the performance of certain sparse matrix operations and solvers (like banded Cholesky factorization).
*   **Key Subroutines/Functions:**
    *   `genrcm(node_num, adj_num, adj_row, adj, perm)`: The main public routine. Takes the graph structure in adjacency list format (`adj_row`, `adj`) and computes the RCM permutation `perm`. It handles graphs with multiple connected components.
        *   It iterates through nodes, using a `mask` to track unvisited nodes.
        *   For each unvisited node `i`, it finds a pseudo-peripheral node `root` within its connected component using `root_find`.
        *   It calls `rcm` to compute the RCM ordering for that component, starting from `root`, storing the result in the appropriate part of `perm`.
        *   It updates the `mask` to mark nodes within the processed component.
    *   `rcm(root, ..., mask, perm, iccsze, ...)`: Performs the Cuthill-McKee ordering for a single connected component starting from `root`.
        *   First, it calls `degree` to find the degree of each node within the component (using `mask`).
        *   It performs a breadth-first search (level set generation) starting from `root`.
        *   Within each level, it orders the newly found neighbors based on their *increasing* degree.
        *   The resulting sequence of nodes in `perm` is the Cuthill-McKee ordering.
        *   Finally, it reverses this sequence (`ivec_reverse`) to get the Reverse Cuthill-McKee ordering.
        *   It updates the `mask` to zero for nodes included in the ordering.
        *   `iccsze` returns the size of the component.
    *   `root_find(root, ..., mask, level_num, level_row, level, ...)`: Finds a pseudo-peripheral node for a component defined by `mask` and an initial `root`.
        *   Generates a level structure using `level_set` starting from `root`.
        *   Selects a node with the minimum degree from the *last* level.
        *   Generates a new level structure starting from this new node.
        *   If the number of levels (`level_num2`) in the new structure is greater than the previous one (`level_num`), it repeats the process (select min degree node from last level, generate new level set).
        *   The process stops when the number of levels does not increase, or if the number of levels equals the component size (line graph). The final starting node is returned as the pseudo-peripheral `root`.
    *   `level_set(root, ..., mask, level_num, level_row, level, ...)`: Performs a breadth-first search starting from `root` to generate levels based on distance. Uses `mask` to consider only relevant nodes. Stores the level structure in `level` (list of nodes) and `level_row` (pointers to start of each level). Updates `mask` to 1 for nodes included in the level set.
    *   `degree(root, ..., mask, deg, iccsze, ls, ...)`: Computes the degree `deg` for each node in the connected component defined by `root` and `mask`. Uses a level set traversal (`ls`) internally. `iccsze` returns the component size.
    *   Other routines (`adj_*`, `d_*`, `i_*`, `perm_*`, `level_set_print`, `sort_heap_external`, `timestamp`, `timestring`, `triangulation_*`): Various helper functions for adjacency list manipulation, printing, sorting, permutations, timing, and potentially graph generation from triangulations (likely examples or utilities not core to RCM itself).

#### 4.3.10 `rota.f90` (Module `crystal_field_d`)

*   **Purpose:** Provides routines to calculate rotation matrices for p and d orbitals and apply rotations to Hamiltonian blocks, primarily used in `TB_ham.f90` to handle crystal field effects when the simulation coordinate system differs from the parameterization's reference axis.
*   **Key Subroutines/Functions:**
    *   `euler_angles(r_orig, r_dest, alpha, beta, gamma)`: Calculates the ZYZ Euler angles (`alpha`, `beta`, `gamma`) that define the rotation taking vector `r_orig` to align with `r_dest`.
    *   `d_rotation(r_orig, r_dest, R)`: Computes the 5x5 rotation matrix `R` representing the rotation from `r_orig` to `r_dest` in the basis of l=2 complex spherical harmonics (|m=-2..+2>). It first calculates Euler angles using `euler_angles` and then uses the Wigner D-matrix formula for l=2.
    *   `p_rotation(r_orig, r_dest, R)`: Computes the 3x3 rotation matrix `R` for p-orbitals (l=1). This is the standard 3D rotation matrix derived from the Euler angles that rotate `r_orig` to `r_dest`.
    *   `tesseral_trans(Rd)`: Transforms a 5x5 rotation matrix `Rd` (originally in the complex spherical harmonic basis) into the basis of real tesseral harmonics (|dxy>, |dyz>, |dz2>, |dxz>, |dx2y2>) via a unitary transformation `U`: `Rd_new = U_dagger * Rd * U`. The matrix `U` defines the transformation between the two bases.
    *   `H_rotation(H, R, HR)`: Applies the rotation `R` to a Hamiltonian block `H` using the similarity transformation `HR = R * H * R_dagger`, where `R_dagger` is the conjugate transpose of `R`.

### 4.4 Structure & Geometry

This section describes modules related to defining, reading, manipulating, and analyzing the atomic structure and lattice geometry.

#### 4.4.1 `struct_building.f90`

*   **Purpose:** Contains high-level routines for reading geometry files (`.upg`), initializing the main data structures (`TStructure`, `ion_basis`, `material_data`), creating the basis, handling dangling bonds, and writing output geometry files (`.gen`). It acts as a bridge between the input geometry file and the internal `ion_basis` representation used for calculations.
*   **Key Subroutines/Functions:**
    *   `init_structure(verbose, str, materials, nr_mat, interfaces, nr_int)`:
        *   **Inputs:** `verbose` level, `str` (TYPE(TStructure) to be filled), `materials` (POINTER to array to be allocated), `nr_mat` (output), `interfaces` (POINTER to 2D array to be allocated), `nr_int` (output).
        *   **Action:** Reads the geometry file specified in `str%gen_filename` (`.upg` format). Parses the header (number of atoms, coordinate type 'C'/'S'). Parses the atom symbol list (`symbols`) to identify unique atom types (`str%atomtypes`). Reads atom lines containing material index, type index, coordinates. Reads lattice vectors (`str%prim`) and origin (`str%start`) if `C_S`='S'. Counts dangling bonds (`str%n_danglings`) based on `hydrosat` symbol. Reads material and interface definitions from the data driver section at the end of the `.upg` file using `read_materials` and `read_interfaces`. Allocates `materials` and `interfaces` arrays. Initializes atom reordering indices (`str%indexa`, `str%inv_indexa`) to move passivation atoms to the end.
        *   **Output:** Populates the `str` structure with raw data, allocates and partially fills `materials` and `interfaces`.
    *   `make_basis(verbose, str, basis)`:
        *   **Inputs:** `verbose` level, `str` (TYPE(TStructure) - input), `basis` (TYPE(ion_basis) - output).
        *   **Action:** Processes the raw data from `str` into the `basis` structure. Allocates members of `basis`. Sets `basis%n_basis` and `basis%n_dg_bond`. Copies `atomtypes`. Converts coordinates (`str%coord`) to fractional coordinates (`basis%coord`) using the inverse primitive vectors (`inv_prim`). Reorders atoms according to `str%indexa` to place passivation atoms at the end. Copies material and type indices. Calculates reciprocal lattice vectors (`basis%rec_latt`). Sets periodicity flags.
        *   **Output:** Populates the `basis` structure.
    *   `init_basis(basis, materials)`:
        *   **Inputs:** `basis` (TYPE(ion_basis) - inout), `materials` (input).
        *   **Action:** Initializes `basis%valence` and `basis%ion` arrays by looking up each atom's type and material index in the `materials` data structure using `check_ion`. Assigns valence 1 to passivation atoms.
        *   **Output:** Fills `basis%valence` and `basis%ion`.
    *   `subs_dg_ions(basis, materials, neig_map)`:
        *   **Inputs:** `basis` (inout), `materials` (input), `neig_map` (input).
        *   **Action:** Implements a specific passivation scheme. It iterates through all atoms `ia`. For each neighbor `ib` of `ia` that is a passivation atom (`hydrosat`), it changes the `basis%type(ib)` to match the *other* atom type in the material `basis%mat(ia)`. (Assumes binary or ternary materials where the non-passivated atom `ia` has a unique counterpart). It also sets `basis%n_st(ib)` to 1. This effectively replaces the electronic properties of the 'Hx' atom with those of a single s-orbital atom of the type it's passivating.
        *   **Output:** Modifies `basis%type` and `basis%n_st` for passivation atoms.
    *   `write_gen(gen_filename, basis, neig_map, rotation, saveH)`:
        *   **Inputs:** Output filename, `basis`, `neig_map`, `rotation` flag, `saveH` flag (include passivation atoms).
        *   **Action:** Writes the structure in the `.gen` format (used by DFTB+). Includes header (number of atoms, periodicity 'S'/'C'), atom type list. Loops through atoms, writes material index, type index, Cartesian coordinates (optionally rotated), number of neighbors, and neighbor indices (adjusting indices for saved H atoms). Writes lattice vectors.
    *   `read_gen(file_num, n_atoms, nn_list, mat, atomtype, coord)`:
        *   **Inputs:** File unit, `n_atoms`.
        *   **Outputs:** `nn_list`, `mat`, `atomtype`, `coord`.
        *   **Action:** Reads atom coordinates and neighbor lists from an already open `.gen` file. Parses lines containing material index, type index, coordinates, number of neighbors, and neighbor list.
    *   `parse_symbols(...)`, `count_fields(...)`, `is_upper(...)`, `pos(...)`, `tokenize(...)`: Helper functions for parsing the atom symbol string in `.upg` files. `tokenize` splits the string, `count_fields` counts tokens, `parse_symbols` stores them in `atomsym` and handles potential formatting issues (like splitting 'GaN' into 'Ga' 'N').
    *   `reorder(str)`:
        *   **Input:** `str` (TYPE(TStructure)).
        *   **Action:** Reorders the atoms within the `str` structure based on the Reverse Cuthill-McKee permutation obtained by calling `genrcm` on the neighbor graph (`str%nn_list`). Updates `coord`, `mat`, `atomtype`, and `nn_list` according to the permutation.
        *   **Output:** Modifies `str` in place.

### `.upg` File Format (related to `struct_building.f90`)

`.upg` files define the atomistic structure input for Uptight. They contain atomic coordinates, atom types, neighbor lists, lattice vectors, and material definitions.

**File Structure Overview:**

- **Header line:**
  
    ```
    <number_of_atoms> <C_or_S>
    ```
  
    - `number_of_atoms`: integer, total number of atoms (including passivation atoms)
    - `C_or_S`: 'C' for Cartesian coordinates, 'S' for scaled (fractional) coordinates with lattice vectors

- **Atom type symbols line:**
  
    ```
    <symbol1> <symbol2> ... <symbolN>
    ```
  
    - List of unique atom symbols (e.g., `Ga As Hx`)
    - Used to map atom type indices in atom data lines

- **Atom data lines:** `number_of_atoms` lines, each either:
  
    - Without neighbor list:
  
        ```
        <material_index> <atom_type_index> <x> <y> <z>
        ```
  
    - Or with neighbor list:
  
        ```
        <material_index> <atom_type_index> <x> <y> <z> <num_neighbors> <neighbor1> <neighbor2> ... <neighborN>
        ```
  
    - where:
        - `material_index`: integer, index of the material this atom belongs to (starting from 1)
        - `atom_type_index`: integer, index into the atom type list (starting from 1)
        - `<x> <y> <z>`: coordinates (Cartesian or fractional depending on header)
        - `num_neighbors`: integer, number of neighbors (excluding self)
        - `neighbor1`...: indices (1-based) of neighboring atoms

- **If `C_or_S` is 'S':** 4 additional lines follow:
  
    ```
    <start_x> <start_y> <start_z>
    <lattice_vector1_x> <lattice_vector1_y> <lattice_vector1_z>
    <lattice_vector2_x> <lattice_vector2_y> <lattice_vector2_z>
    <lattice_vector3_x> <lattice_vector3_y> <lattice_vector3_z>
    ```
  
    - `start`: origin offset vector
    - 3 lattice vectors (columns of the lattice matrix), in Angstroms

- **Material definitions:**
  
    - First line:
  
        ```
        <string> <number_of_materials>
        ```
  
        (e.g., `materials 2`)
  
    - Then, for each material, one line with:
  
        ```
        <material_index> <name> <crystal_type> <material_type> <num_parents> <mixing_type> <parent1_name> <parent1_content> <parent1_datafile> ... <gap_corrections>
        ```
  
        (see Section 5 for details on material parameters)

- **Interface definitions (optional):**
  
    - Lines defining interfaces between materials, following the material definitions
    - See `read_interfaces` in `struct_building.f90` for details

**Notes:**

- Atom indices in neighbor lists are 1-based.
- Passivation atoms (e.g., Hydrogen) are included in the atom list and can be identified by their atom type symbol (e.g., 'Hx').
- The order of atoms in the file determines their indices.
- The neighbor list is optional; if omitted, neighbors will be generated automatically.
- The lattice vectors are only present if the header specifies 'S' (scaled coordinates).
- Material and interface definitions follow the atomic structure section and are parsed similarly to `.data` files (see Section 5).

#### 4.4.2 `neighbours.f90`

*   **Purpose:** Contains routines for building, refining, and managing the nearest-neighbor map (`nn_map`) for all atoms in the structure, considering periodicity and interaction order.
*   **Key Derived Type:**
    *   `nearest_neighbours`: Stores neighbor information for a single atom.
        *   `dist` (REAL(dp), POINTER, DIMENSION(:)): Array of distances to neighbors (Angstrom).
        *   `vec` (INTEGER, POINTER, DIMENSION(3,:)): Array of lattice vectors (image cell offsets in units of primitive vectors) for each neighbor. `vec(:,j)` corresponds to `ind(j)`.
        *   `ind` (INTEGER, POINTER, DIMENSION(:)): Array of atom indices for each neighbor (1 to `n_basis + n_dg_bond`).
        *   `order` (INTEGER, POINTER, DIMENSION(:)): Array indicating neighbor order (0=self, 1=1st NN, 2=2nd NN, etc.).
        *   `n_cpl` (INTEGER): Number of unique neighbor atoms (excluding self and periodic images within the central cell).
*   **Key Subroutines/Functions:**
    *   `create_neighbours_map(nn_map, natoms)`, `destroy_neighbours_map(nn_map)`, `delete_near(near)`: Allocate/deallocate the main neighbor map array (`nn_map`, size `natoms`) and its pointer members (`ind`, `dist`, `vec`, `order`) for individual atoms.
    *   `make_neighbours_map(str, basis, mat_data, neig_map)`: Builds the initial neighbor map when no neighbor list is provided in the input (`.upg`).
        *   Calls `select_nearest_neighbours` for each atom `i` to find all potential neighbors up to the `max_order` required by its material.
        *   Allocates and populates `neig_map(i)%ind`, `order`, `dist`, `vec`.
        *   Counts dangling bonds (`basis%n_dg(i)`).
        *   Sorts the neighbors by index (`sort_near_by_ind`).
        *   Counts unique neighbors (`neig_map(i)%n_cpl`).
    *   `refine_neighbours_map(str, basis, mat_data, neig_map)`: Refines an existing neighbor list (typically 1st NN read from `str%nn_list`) by adding higher-order neighbors if needed.
        *   Initializes `neig_map` based on `str%nn_list`.
        *   Calculates distances and lattice vectors for the initial neighbors considering periodicity (`lattice_vectors`).
        *   Sorts initial neighbors by distance and determines their order (currently hardcoded to 1).
        *   If `mat_data(i_mat)%max_order > 1`, it searches for 2nd (and potentially higher) order neighbors by examining neighbors-of-neighbors.
        *   For each potential higher-order neighbor `ib`, it checks if parameters exist for that order (`check_pair`).
        *   If parameters exist, it calls `nearest_test` to find all periodic images of `ib` within the expected distance range (`dist_ref`) and adds them to temporary lists.
        *   Reallocates and updates `neig_map(i)` with the combined list of neighbors.
        *   Sorts the final list by index (`sort_near_by_ind`).
        *   Counts unique neighbors (`neig_map(i)%n_cpl`).
    *   `select_nearest_neighbours(i_a, basis, mat_data, nn_ind, nn_order, nn_dist, nn_vec)`: Finds all neighbors (`nn_ind`) for atom `i_a` up to the `max_order` required by its material `basis%mat(i_a)`.
        *   Loops through interaction orders `i_ord` from 1 to `max_order`.
        *   Loops through all potential neighbor atoms `i_n`.
        *   Checks if parameters exist for the pair (`i_a`, `i_n`) at order `i_ord` using `check_pair` or `check_interface_pair`.
        *   If parameters exist, calls `nearest_test` to find relevant periodic images and add them to temporary lists.
        *   Allocates and returns the final neighbor lists (`nn_ind`, `nn_order`, `nn_dist`, `nn_vec`).
    *   `nearest_test(i_a, i_b, basis, ref_dist, i_ord, n_n, tmp_ind, tmp_ord, tmp_dist, tmp_vec)`: Checks if atom `i_b` (and its periodic images) is a neighbor of `i_a` at order `i_ord`.
        *   Calculates the vector `vec` from `i_b` to `i_a` in Cartesian coordinates.
        *   Loops through all lattice vectors `t_vec` (from `lattice_vectors`).
        *   Calculates the distance `dist = norm(vec - prim * t_vec)`.
        *   If `dist` is close to `ref_dist` (within 0.3 Angstrom tolerance) and this specific image (`i_b`, `t_vec`) is not already found (`already_in`), adds `i_b`, `i_ord`, `dist`, and `t_vec` to the temporary lists and increments `n_n`.
    *   `sort_near_by_ind(near)`: Sorts the `ind`, `order`, `dist`, `vec` arrays within a `nearest_neighbours` structure based on ascending `ind` values.
    *   `sort_near_by_dist(near)`: Sorts based on ascending `dist` values (marked as potentially not working).
    *   `is_dg_bond(i_n, basis, current_near)`: Checks if the neighbor entry `i_n` in `current_near` corresponds to a dangling bond. Returns true if the neighbor index `ind(i_n)` is greater than `n_basis` (i.e., it's a passivation atom) OR if the connection involves a non-zero lattice vector component along a direction specified as non-periodic in `basis%periodic_BC`.
    *   `check_input_nn_list(str)`, `check_nn_map(nn_map)`: Verify the symmetry of neighbor lists (if A is neighbor of B, B must be neighbor of A). Stops execution if asymmetry is found.
    *   `write_neighbours_map(nn_map)`, `write_am_coo(basis, nn_map)`: Output routines for neighbor information, `write_am_coo` writes in a simple `i j 1` format.
    *   `already_in(nn, k, ind, vec, vec_t)`: Helper function. Checks if atom `k` with lattice vector `vec_t` is already present in the first `nn-1` entries of the `ind` and `vec` arrays.
    *   `reallocate_i`, `reallocate_d`, `reallocate_i2`: Helper routines to dynamically resize temporary arrays during neighbor list construction.

### 4.5 Tight-Binding Model & Hamiltonian

This section describes the modules responsible for setting up the tight-binding parameters, handling alloys, and constructing the Hamiltonian matrix.

#### 4.5.1 `states_and_couplings.f90`

*   **Purpose:** Initializes reference lists for states and couplings, sorts parameters read from input files according to these references, and provides helper functions related to states. Ensures consistency between parameter files and internal representation.
*   **Key Subroutines/Functions:**
    *   `ref_states_and_couplings(ref_states, n_ref_st, ref_couplings, n_ref_cpl)`:
        *   **Outputs:** `ref_states` (POINTER to CHARACTER array), `n_ref_st` (INTEGER), `ref_couplings` (POINTER to CHARACTER array), `n_ref_cpl` (INTEGER).
        *   **Action:** Allocates and initializes the global reference arrays `ref_states` (e.g., 's', 'px', ...) and `ref_couplings` (e.g., 'sss', 'sps', ...) with the standard ordering defined in the `globals` module. Sets the corresponding sizes `n_ref_st` (10) and `n_ref_cpl` (21). These arrays are typically associated with pointers in the `OUPT` type.
    *   `init_n_st(basis, mat_data)`:
        *   **Inputs:** `basis` (TYPE(ion_basis)), `mat_data` (POINTER to array of TYPE(material_data)).
        *   **Action:** Calculates and stores the number of basis states (`n_st`) for each atom in the `basis%n_st` array. It determines this by looking up the atom's material and ion type and finding the size of the corresponding `state` array in `mat_data%ion`. Uses `number_states_atom`.
        *   **Output:** Modifies `basis%n_st`.
    *   `number_states_atom(basis, i_atom, mat_data)`:
        *   **Inputs:** `basis`, atom index `i_atom`, `mat_data`.
        *   **Output:** INTEGER (number of states).
        *   **Action:** Finds the material (`i_mat`) and ion (`i_ion`) index corresponding to `i_atom` using `check_ion`. Returns the size of the `state` array for that ion type (`mat_data(i_mat)%ion(i_ion)%state`).
    *   `set_max_order(materials)`:
        *   **Input:** `materials` (POINTER to array of TYPE(material_data)).
        *   **Action:** Iterates through all materials and their parent definitions. For each material, it finds the maximum value of `order` among all `pair_coupling` entries in its first parent and stores it in `materials(i)%max_order`.
        *   **Output:** Modifies `materials(:)%max_order`.
    *   `sort_states(mat_data, ref_states, ref_couplings)`:
        *   **Inputs:** `mat_data` (TYPE(material_data) - modified in place), `ref_states`, `ref_couplings`.
        *   **Action:** This crucial routine ensures that the orbital states (`ion%state`, `ion%energy`) and coupling parameters (`pair%cpl`, `pair%energy`, `pair%scaling`, Tan factors) within the `mat_data` structure (specifically within its `parent%ion` and `parent%pair` arrays) are reordered to match the standard sequence defined by `ref_states` and `ref_couplings`. It uses `check_ref_order` and `check_ref` to find the mapping. It also populates the `ind_ref` (map to reference index) and `ind_ref_inv` (inverse map) arrays within the `ion_orbit` type. For couplings, it reallocates the arrays to the full size `n_ref_cpl` and fills them according to the reference order, padding with zeros where necessary.
        *   **Output:** Modifies the `ion` and `pair` members within `mat_data%parent` arrays.
    *   `sort_couplings(...)`: (Seems unused or internal helper for `sort_states`) Potentially involved in sorting coupling parameters.
    *   `states_sym(orb, n_states)`: (Called by `input_data.f90`) Expands shorthand orbital names (like 'p', 'd') into their components ('px', 'py', 'pz', 'dxy', etc.) based on standard degeneracy rules. Returns a character array of state names.

#### 4.5.2 `alloys.f90`

*   **Purpose:** Handles the setup of material parameters specifically for alloys, implementing the Virtual Crystal Approximation (VCA) or preparing for random alloy treatment based on input flags.
*   **Key Subroutines/Functions:**
    *   `init_mat_ion(mat_data)`:
        *   **Input:** `mat_data` (TYPE(material_data) - modified in place).
        *   **Action:** Initializes the `ion` list (`mat_data%ion`) for the alloy material.
            *   For simple/binary materials with one parent, it simply copies the parent's `ion` data.
            *   For binary alloys like SiGe (treated as ternary with 2 parents), it calls `ternary_states_uncommon`.
            *   For ternary alloys (e.g., AlGaAs), it calls `ternary_states_common` to handle the common atom (As) and `ternary_states_uncommon` for the alloyed sublattice (Al, Ga).
            *   For quaternary alloys, it calls `alloy_states_nomixing`.
            *   It also calculates VCA-averaged lattice parameters (`lat_par`, `u_par`, `int_str_par`) based on parent contents.
        *   **Output:** Populates `mat_data%ion` and averaged lattice parameters.
    *   `ternary_states_common(ion, parent, i_ion, content, bowing, alloy_random)`:
        *   **Inputs:** `ion` (output array), `parent` (input array), `i_ion` (index for common ion), `content`, `bowing`, `alloy_random` flag.
        *   **Action:** Finds the common ion present in both parents. Performs a VCA average of its `offset`, `energy`, `so_energy`, and `b_d` parameters, weighted by `content`. Applies bowing correction quadratically dependent on concentrations to `energy` and `so_energy`. Stores the averaged parameters in `ion(i_ion)`.
    *   `ternary_states_uncommon(ion, parent, i_ion, content, bowing, alloy_random, average)`:
        *   **Inputs:** `ion` (output array), `parent` (input array), `i_ion` (current index, updated), `content`, `bowing`, `alloy_random`, `average` flags.
        *   **Action:** Handles the ions that differ between the two parents.
            *   If VCA (`alloy_random = .false.` or `average = .true.`): Performs VCA averaging and bowing similar to `ternary_states_common` and stores the result in `ion(i_ion+1)`. Increments `i_ion`.
            *   If Random Alloy (`alloy_random = .true.` and `average = .false.`): Stores the parameters for *both* differing ion types separately in `ion(i_ion+1)` and `ion(i_ion+2)`. Increments `i_ion` twice.
    *   `alloy_states_nomixing(ion, parent)`:
        *   **Inputs:** `ion` (output array), `parent` (input array).
        *   **Action:** Used for quaternary (or more complex) alloys where simple averaging might not apply. It iterates through all parents and their ions, adding each *unique* ion type found (based on name) to the output `ion` array, copying its parameters directly from the first parent it was found in. No averaging or bowing is performed.
    *   `random_alloy_common(...)`, `random_alloy_uncommon(...)`:
        *   **Inputs:** `atom_name` (CHARACTER array, inout), `n_atom`, `conc` (concentration), `ref_name` (names of constituent atoms).
        *   **Action:** These routines modify the `atom_name` array *after* the initial structure is built, simulating a random alloy by substituting atoms. They calculate the number of atoms to substitute based on `conc` and randomly select sites from the relevant sublattice (`_common` assumes a common anion/cation, `_uncommon` assumes substitution on all sites like SiGe) to change their type. *Note: These seem intended for pre-processing or specific workflows, not typically called during standard Hamiltonian construction.*

#### 4.5.3 `TB_ham.f90`

*   **Purpose:** This is the central module for constructing the tight-binding Hamiltonian matrix (`H`) and potentially the time-reversal operator (`U`) in Compressed Sparse Row (CSR) format. It combines structural information (neighbor lists, distances, coordinates) with material parameters (onsite energies, couplings, spin-orbit) according to the chosen TB model (Jancu or Tan) and applies effects like strain, k-vector phase, potential, and passivation.
*   **Key Subroutines/Functions:**
    *   `sparse_ham(upt)`: The main Hamiltonian construction routine.
        *   **Input:** `upt` (TYPE(OUPT) containing all necessary data).
        *   **Action:**
            1.  Initializes Hamiltonian size (`n_ham`) and estimates non-zeros (`nnz`) for allocation. Allocates `upt%ham` (and `upt%U` if `relat`).
            2.  Determines MPI parallelization range (`p_start`, `p_stop`) for the outer loop over atoms.
            3.  **Outer Loop (Atoms `i_a`):** Iterates through atoms assigned to the current MPI process.
                a.  Gets neighbor list `current_near` for atom `i_a`.
                b.  Identifies material (`i_a_mat`) and ion type (`i_a_ion`) of `i_a`. Gets reference orbital mapping (`a_ref`, `inv_ref`).
                c.  Initializes temporary storage for onsite energy (`onsite`), SO coupling (`so_cpl`), and Tan scheme corrections (`intra_cpl`, etc.).
                d.  **Inner Loop (Neighbors `i_n`):** Iterates through neighbors `i_b` of `i_a` (including `i_a` itself for the onsite block).
                    i.  Determines if the bond is dangling (`is_dg_bond`).
                    ii. Identifies the relevant material parameters (`interface_data`, `p_parent`, `p_pair`) for the `i_a`-`i_b` interaction, handling interfaces correctly (`check_pair`, `check_interface_pair`, `check_uncommon_interface_pair`).
                    iii. **Onsite Block (`i_a == i_b`):** Accumulates VCA-averaged onsite energies and SO couplings from neighbors (Jancu scheme). Calculates Tan scheme onsite corrections (`get_ons_corr`, `get_so_corr`). Stores results in `onsite`, `so_cpl`, `intra_cpl`.
                    iv. **Offsite Block (`i_a != i_b`):**
                        1.  Calculates bond vector (`D_latt`) and direction cosines (`cos_latt`).
                        2.  Calculates k-vector phase factor `exp_fac = EXP(j*k.D_latt)`.
                        3.  Retrieves two-center parameters `tb_cpl` from `p_pair`, applying Harrison scaling (`harrison_scaling`) and Tan corrections (`add_dip_corr`, `get_quad_corr`) if applicable.
                        4.  Calls `koster_slater` to get the interaction block `tb_bloc` in the reference basis.
                        5.  Maps `tb_bloc` to the actual orbital basis sizes (`n_st_a`, `n_st_b`) using `a_ref`, `b_ref` and adds `exp_fac * tb_bloc` to the corresponding temporary coupling block `cpl(i_cpl)%mat`.
                    v.  **Dangling Bonds:** If `dg_bond` is true, calculates the interaction using scaled parameters (`d_H`) via `koster_slater` and stores it in a separate temporary `hydro` block.
                e.  **Post-Neighbor Loop:**
                    i.  Adds external potential (`pot_data`) to `onsite`.
                    ii. Applies crystal field rotations/splitting (`rotate_p`, `rotate_d`, `crystal_field_zb`) to the diagonal block `h_diag%mat` based on `onsite` energies (Jancu scheme).
                    iii. Adds `h_diag%mat` and Tan intra-atomic terms (`intra_cpl`) to the main onsite block `cpl(i_onsite)%mat`.
                    iv. Applies passivation corrections (`Klimeck_passiv` or simple scaling) to onsite/offsite blocks if dangling bonds exist.
                f.  **Spin Loop:** Iterates through spin combinations (`i_spin_a`, `i_spin_b`).
                    i.  Calculates spin-orbit blocks `so_diag`, `so_off_diag` using `spin_sparse`.
                    ii. Assembles the final blocks for the CSB structure `M` (and `UM` if `relat`) by combining `cpl` blocks with `so_diag` (spin-diagonal) or `so_off_diag` (spin-off-diagonal).
                    iii. Stores block column indices (`M%Row(sp_a)%col(sp_b)`).
                g.  Converts the CSB row (`M`, `UM`) to CSR format (`csb_to_csr`) and appends it to the global `upt%ham` and `upt%U` matrices.
                h.  Deallocates temporary block storage (`cpl`, `hydro`, `h_diag`).
            4.  Finalizes CSR row pointers (`upt%ham%Mi`, `upt%U%Mi`).
            5.  Prints memory usage statistics.
        *   **Output:** Populates `upt%ham` and `upt%U` (if `relat`) with the Hamiltonian/operator in CSR format.
    *   `koster_slater(cos_latt, t, v)`:
        *   **Inputs:** `cos_latt` (direction cosines l,m,n), `t` (array of two-center integrals like t(sss), t(sps), etc., ordered by `globals` indices).
        *   **Output:** `v` (2D REAL(dp) array, size `n_ref_states` x `n_ref_states`) containing the Slater-Koster transformed matrix elements in the reference orbital basis.
        *   **Action:** Implements the standard Slater-Koster transformation formulas for s, p, s*, d orbitals based on the direction cosines (l,m,n) and the input two-center integrals `t`.
    *   `spin_sparse(i_spin_a, so, diag, off_diag)`:
        *   **Inputs:** `i_spin_a` (1 for up, 2 for down), `so` (REAL(dp) array containing SO parameters Delta_p, Delta_d).
        *   **Outputs:** `diag`, `off_diag` (COMPLEX(dp) matrices, size `n_ref_states` x `n_ref_states`).
        *   **Action:** Calculates the matrix elements of the spin-orbit operator `L.S` in the reference orbital basis. Returns the spin-diagonal part (e.g., <up,px|L.S|up,py>) in `diag` and the spin-off-diagonal part (e.g., <up,px|L.S|down,pz>) in `off_diag`.
    *   `harrison_scaling(...)`: Applies distance-dependent scaling `(d_ref / d_actual)^n` to two-center integrals `tb_cpl`. Handles VCA averaging for alloys.
    *   `get_ons_corr`, `get_so_corr`, `add_dip_corr`, `get_quad_corr`, `update_intra_cpl`, `get_M_dip`, `get_M_quad`: Helper functions specific to the Tan parameterization scheme, calculating various corrections.
    *   `rotate_p`, `rotate_d`, `crystal_field_zb`: Apply rotations and crystal field splitting to onsite energies (Jancu scheme).
    *   `hydrogen_coupling`, `Klimeck_passiv`: Specific passivation schemes for dangling bonds.
    *   `check_if_hermitian`, `check_if_antihermitian`, `check_if_real`, `hermitianize`: Utility functions for matrix properties.
    *   `get_ion_block_size`, `get_ion_orbitals`: Helper functions.

### 4.6 Solvers

This section describes the different numerical methods implemented or interfaced for solving the eigenvalue problem `H|psi> = E|psi>`, where H is the sparse Hamiltonian matrix. The choice of solver depends on the system size and the desired eigenvalues:
*   **LAPACK (`lapack_driver.f90`)**: Direct diagonalization, suitable for small systems where the full dense matrix can be handled. Finds all eigenvalues.
*   **Lanczos (`lanczos_driver.f90`) / ARPACK (`arpack.f90`)**: Iterative methods, efficient for finding extremal (lowest/highest) eigenvalues of large sparse matrices.
*   **Jacobi-Davidson (`JD_driver.f90`)**: Iterative method, often good for finding eigenvalues near a specific target energy (interior eigenvalues) or a cluster of eigenvalues.
*   **FEAST (`feast_driver.f90`)**: Contour integration method, finds all eigenvalues within a specified energy range [`Emin`, `Emax`].

#### 4.6.1 Lanczos Solver (`lanczos_driver.f90`, `lanczos.F90`, `lanczos_cuda*.cu`)

*   **Purpose:** Implements the Lanczos algorithm, an iterative method particularly efficient for finding extremal (lowest or highest) eigenvalues and corresponding eigenvectors of large, sparse, Hermitian matrices. It works by constructing a small tridiagonal matrix (T) that approximates the original Hamiltonian within a Krylov subspace.
*   **Algorithm:** The implementation targets eigenvalues of `A = (H - lambda*I)^2`, where `lambda` is an energy shift (guess). Finding the lowest eigenvalue of `A` corresponds to finding the eigenvalue of `H` closest to `lambda`. It uses the Parravicini-Grosso restart scheme.
*   **Key Subroutines/Functions:**
    *   `lanczos(upt)` (`lanczos_driver.f90`): High-level driver.
        *   **Input:** `upt` (TYPE(OUPT)). Requires `upt%ham`, `upt%num_vb`, `upt%num_cb`, `upt%lambda_vb`, `upt%lambda_cb`, solver parameters.
        *   **Action:** Allocates `upt%eigen_values`, `upt%eigen_vectors`, `upt%particles`. Calls `LANCZOS_EV` separately for valence band (sign=-1, shift=`lambda_vb`) and conduction band (sign=1, shift=`lambda_cb`). Handles spin degeneracy by constructing the degenerate partner state using the time-reversal operator `upt%U`. Writes results using `append_eigenstate`.
        *   **Output:** Populates `upt%eigen_values`, `upt%eigen_vectors`, `upt%particles`.
    *   `LANCZOS_EV(...)` (`lanczos.F90`): Core Lanczos implementation driver.
        *   **Inputs:** Hamiltonian `H`, overlap `U`, solver parameters, target energy `lambda`, `sign` (+1 for conduction, -1 for valence), etc.
        *   **Outputs:** `energies`, `eigen_vectors`.
        *   **Action:** Selects the backend based on `solver_flag`. Applies the energy shift `lambda` to `H` using `sprs_shift`. Calls the backend (`fast_lanczos_ev_*`). Removes the shift from `H`. Calculates final energies `E = +/-sqrt(E_lanczos) + shift_total`.
    *   `fast_lanczos_ev_*` (`lanczos.F90`, `lanczos_cuda*.cu`): Backend iterative routines (Serial, MPI/OpenMP, CUDA).
        *   **Inputs:** Shifted Hamiltonian (or its components), solver parameters, initial guess vector `eigen_seed`, previously found eigenvectors `eigen_v`.
        *   **Outputs:** `eigen_seed` (converged eigenvector), `energy` (eigenvalue of A), `deltaE` (error estimate).
        *   **Action:**
            1.  Initializes Lanczos vectors `|0>` (from `eigen_seed`), `|-1> = 0`.
            2.  **Main Loop:** Iterates `j` from 0 up to `nstep`.
                *   Calculates `|aux> = A |j> = (H-lambda*I)^2 |j>` (using two `sprs_ax` calls).
                *   Calculates diagonal element `alpha = <j|A|j>`.
                *   Calculates next vector `|j+1> = |aux> - alpha*|j> - beta*|j-1>`.
                *   Orthogonalizes `|j+1>` against previous eigenvectors (`project_out`).
                *   Calculates off-diagonal element `beta = norm(|j+1>)`.
                *   Stores `alpha` and `beta` in tridiagonal matrix arrays (`ad2`, `ad1`).
                *   Reorthogonalizes `|j+1>` against `|j>` and `|j-1>` (implicit in formula).
                *   Updates vectors: `|j-1> <- |j>`, `|j> <- |j+1>/beta`.
                *   Checks orthogonality against initial seed (`ort_chk`) periodically and increases `nstep` if needed and possible.
            3.  Diagonalizes the resulting `nstep` x `nstep` tridiagonal matrix `T` using LAPACK's `dstevx` to get Ritz values (`eigen_val`) and Ritz vectors (`eigen_vec`).
            4.  Checks for convergence using `fast_tol` (based on variance of last 10 eigenvalues) and `long_tol` (based on residual estimate `deltaE`). Switches between `min_step` and `long_step` iterations.
            5.  Reconstructs the approximate eigenvector (Ritz vector) `|psi>` of `A` in the full space using `|psi> = Sum_j eigen_vec(j,1) * |j>`.
            6.  Calculates refined eigenvalue `energy = <psi|A|psi>` using `test_eigvect`.
            7.  Calculates error estimate `deltaE = | energy - eigen_val(1) |`.
            8.  If not converged, updates `eigen_seed = |psi>` and repeats the main loop.
    *   `project_out_*`: Orthogonalizes a vector against previously found eigenvectors using Gram-Schmidt.
    *   `exchange_vector`, `gather_on_master`: MPI communication routines.
    *   CUDA versions implement core steps using cuSPARSE (`cusparseDcsrmv`, `cusparseZcsrmv`) and cuBLAS (`cublasDznrm2`, `cublasZdotc`) kernels, potentially with custom kernels for vector updates (`scl_mul_vct_kernel`, etc.).

#### 4.6.2 Jacobi-Davidson Solver (`JD_driver.f90`, `JD.F90`, `JD_N_PC*.c`/`.cu`)

*   **Purpose:** Implements the Jacobi-Davidson (JD) algorithm, an iterative method often effective for finding interior eigenvalues or a few eigenvalues near a target energy (`shift`). It iteratively refines approximations to eigenpairs by solving a correction equation. This implementation appears to be without preconditioning ("no_pc").
*   **Algorithm:** The core idea is to find corrections `t` orthogonal to the current approximate eigenvector `u` by solving `(I - u*u_dagger)*(A - theta*I)*(I - u*u_dagger) * t = -r`, where `r = A*u - theta*u` is the residual and `theta` is the current Ritz value (eigenvalue approximation). The basis `V` is then expanded with `t`.
*   **Key Subroutines/Functions:**
    *   `jd(upt)` (`JD_driver.f90`): High-level driver. Similar structure to `lanczos`, calls `JD_EV`.
    *   `JD_EV(...)` (`JD.F90`): Core JD implementation driver.
        *   **Inputs:** Hamiltonian `H`, overlap `U`, solver parameters, target energy `lambda`, `sign`, etc.
        *   **Outputs:** `energies`, `eigen_vectors`.
        *   **Action:** Selects backend based on `solver_flag`. May split `H` into real/imaginary parts (`split_matrix_sp_mx_prec`) for the mixed-precision CUDA solver. Calls the backend (`jd_*_no_pc_*`). Calculates final energies `E = lambda_jd` (JD directly targets eigenvalues near the shift).
    *   `jd_*_no_pc_*` (`JD.F90`, `JD_N_PC*.c`/`.cu`): Backend routines implementing the JD algorithm.
        *   **Inputs:** Hamiltonian components, solver parameters (`JD_tol`, `JD_Min_step`, `JD_Max_step`, `Shift`, `Num_ev`), linear solver parameters (`LS_tol`, `LS_restart`, `LS_maxit`).
        *   **Outputs:** `lambda_out` (eigenvalues), `eigen_vec_out` (eigenvectors).
        *   **Action:**
            1.  Initializes search subspace `V` (size `m`) with a starting vector.
            2.  **Main Loop:** Iterates until `k = Num_ev` eigenvalues are found.
                *   Applies operator `A = H - shift*I` to the latest basis vector `t` to get `w = A*t`.
                *   Orthogonalizes `w` and `t` against previous basis vectors `V` and `W` (Modified Gram-Schmidt). Normalizes `w` and `t` to get new basis vectors `v_m`, `w_m`.
                *   Constructs the projected matrix `M_ij = <v_i | A | v_j>`.
                *   Solves the small eigenvalue problem `M*y = theta*y` using LAPACK (`zheevr`) to get Ritz values `theta` and Ritz vectors `y`. Sorts Ritz pairs based on proximity to zero (target).
                *   Selects the target Ritz pair (`theta_1`, `y_1`).
                *   Computes the corresponding approximate eigenvector `u = V*y_1` and `Au = W*y_1`.
                *   Calculates the residual `r = Au - theta_1*u`.
                *   Checks convergence: `IF norm(r) < JD_tol THEN`.
                    *   Accept `lambda = theta_1 + shift` as an eigenvalue and `u` as the eigenvector. Store them.
                    *   Deflate: Remove the converged eigenvector from the search space (effectively restarting the subspace `V`, `W`, `M` with the remaining Ritz vectors). Decrement `m`.
                    *   If `k == Num_ev`, exit.
                    *   Continue to correction equation step for the *next* target Ritz pair.
                *   **Correction Equation:** Solve `(I - u*u_dagger)*(A - theta_1*I)*(I - u*u_dagger) * t = -r` approximately for `t` using GMRES (`GMRES_CPU` or `gmres` in CUDA).
                *   Orthogonalize the correction vector `t` against the current basis `V`.
                *   Normalize `t` and add it as the new basis vector `v_{m+1}`. Increment `m`.
                *   Handle subspace restarts if `m >= jd_max_step`.
    *   `GMRES_CPU`, `gmres` (in C/CUDA): Implements the Generalized Minimum Residual iterative method for solving the linear correction equation.
    *   C/CUDA helper kernels (`vct_*`, `spmv_*`, `shift_A`): Perform basic vector operations and sparse matrix-vector products optimized for CPU (using OpenMP/MKL) or GPU (using CUDA/cuBLAS/cuSPARSE).

#### 4.6.3 LAPACK Solver (`lapack_driver.f90`, `lapack_diag.f90`)

*   **Purpose:** Provides an interface to LAPACK routines for exact, direct diagonalization of the full Hamiltonian matrix. This is only feasible for small systems where the dense `N x N` matrix can fit into memory and be diagonalized efficiently (typically O(N^3) complexity).
*   **Key Subroutines/Functions:**
    *   `lapack(upt)` (`lapack_driver.f90`): Main driver routine.
        *   **Input:** `upt` (TYPE(OUPT)).
        *   **Action:**
            1.  Allocates a dense complex matrix `ham(n_ham, n_ham)`.
            2.  Calls `assemble_dense_H` to convert the sparse `upt%ham` into the dense `ham`.
            3.  Allocates temporary storage `tmp_eigvals(n_ham)` for all eigenvalues.
            4.  Calls `diagonalize_ham` to diagonalize the dense matrix `ham`. The eigenvalues are returned in `tmp_eigvals` and eigenvectors overwrite `ham`.
            5.  Allocates the output arrays `upt%eigen_values` and `upt%eigen_vectors` (size `num_ev`).
            6.  Sorts `tmp_eigvals` (implicitly by the LAPACK routine). Finds the index `i_k` corresponding to the highest valence band (or lowest energy state if `lambda_vb` is very low).
            7.  Copies the `upt%num_vb` eigenvalues/vectors *below* `lambda_vb` from `tmp_eigvals`/`ham` into `upt%eigen_values(1:num_vb)` / `upt%eigen_vectors(:, 1:num_vb)`.
            8.  Copies the `upt%num_cb` eigenvalues/vectors *above* the highest valence state found into `upt%eigen_values(num_vb+1:num_ev)` / `upt%eigen_vectors(:, num_vb+1:num_ev)`.
            9.  Sets particle type flags in `upt%particles`.
            10. Deallocates `ham`, `tmp_eigvals`.
        *   **Output:** Populates `upt%eigen_values`, `upt%eigen_vectors`, `upt%particles`.
    *   `assemble_dense_H(M, Mj, Mi, sp_fmt, nrows, ham)` (`lapack_diag.f90`): Converts a CSR sparse matrix (`M`, `Mj`, `Mi`) into a dense complex matrix `ham`. Handles different sparse formats ('U', 'L', 'F').
    *   `diagonalize_ham(HAM, N, eigval)` (`lapack_diag.f90`): Wrapper for LAPACK's `ZHEEVD` routine (complex Hermitian eigenvalue problem, divide and conquer). Computes all eigenvalues (returned in `eigval`) and eigenvectors (overwriting `HAM`).
    *   `diagonalize_ham_i(HAM, N, Emin, Emax, eigval, eigvec, num_conv)` (`lapack_diag.f90`): Wrapper for LAPACK's `ZHEEVX` routine (expert driver). Computes eigenvalues within the range [`Emin`, `Emax`] and corresponding eigenvectors. Returns the number of converged eigenvalues `num_conv`.

#### 4.6.4 ARPACK Solver (`arpack.f90`)

*   **Purpose:** Provides an interface to the ARPACK library, which implements implicitly restarted Arnoldi/Lanczos methods. Offers similar functionality to the internal Lanczos solver but relies on the external library installation.
*   **Key Subroutines/Functions:**
    *   `arpack_dr(upt)`: Main driver routine.
        *   **Input:** `upt` (TYPE(OUPT)).
        *   **Action:** Allocates `upt%eigen_values`, `upt%eigen_vectors`. Calls `arpack_zh` separately for valence band (shift `lambda_vb`) and conduction band (shift `lambda_cb`). Calculates final energies `E = +/-sqrt(E_arpack) + shift`.
        *   **Output:** Populates `upt%eigen_values`, `upt%eigen_vectors`.
    *   `arpack_zh(maxn, maxnev, maxncv, max_arn, tol, eigen_values, eigen_vectors, M, Mij, sp_fmt)`: Wrapper around ARPACK routines.
        *   **Inputs:** Matrix dimensions (`maxn`), number of eigenvalues requested (`maxnev`), size of Arnoldi basis (`maxncv`), max iterations (`max_arn`), tolerance (`tol`), sparse matrix (`M`, `Mij`, `sp_fmt`).
        *   **Outputs:** `eigen_values`, `eigen_vectors`.
        *   **Action:**
            1.  Sets up ARPACK parameters (`iparam`, `which='SM'` for smallest magnitude eigenvalues of the shifted operator).
            2.  Uses a **reverse communication** loop with `znaupd`:
                *   Call `znaupd`.
                *   `znaupd` returns with `ido` indicating the required operation.
                *   If `ido` is -1 or 1, it requests `y <- OP*x`. The wrapper calculates `y = (H-shift*I)^2 * x` using two calls to `sprs_ax`. The input `x` and output `y` vectors are taken from/put into the `workd` array at locations specified by `ipntr`.
                *   Call `znaupd` again.
            3.  Loop continues until `znaupd` returns `ido=99` (convergence or max iterations).
            4.  Calls `zneupd` to post-process the results, compute converged Ritz values (`eig_values`) and Ritz vectors (`eig_vectors`).
            5.  Calculates residual norms `|| A*x - lambda*x ||` for converged pairs.
            6.  Copies results to output arrays.

#### 4.6.5 FEAST Solver (`feast_driver.f90`)

*   **Purpose:** Provides an interface to the FEAST eigenvalue solver library. FEAST uses a contour integration technique in the complex plane to find *all* eigenvalues located within a specified energy interval [`Emin`, `Emax`].
*   **Key Subroutines/Functions:**
    *   `feast(upt)`: Main driver routine.
        *   **Input:** `upt` (TYPE(OUPT)).
        *   **Action:**
            1.  Initializes FEAST parameters using `feastinit`. Sets specific parameters (e.g., `feastparam(1)=1` for verbose output).
            2.  Defines the energy search interval [`Emin`, `Emax`] using `upt%lambda_vb` and `upt%lambda_cb`.
            3.  Sets an initial guess `M0` for the number of eigenvalues within the interval (e.g., `upt%num_cb`).
            4.  Allocates arrays for eigenvalues (`E`), eigenvectors (`X`), and residuals (`res`).
            5.  Calls the main FEAST routine `zfeast_sst` (complex Hermitian standard solve). FEAST performs the contour integration and subspace iterations internally.
            6.  Checks the return `info` flag for errors.
            7.  If successful, copies the found eigenvalues `E(1:M)` and eigenvectors `X(:,1:M)` (where `M` is the actual number found) into `upt%eigen_values` and `upt%eigen_vectors`. *Note: This implementation seems to only store results based on `M0` (initial guess) rather than `M` (actual found), potentially missing some states or causing errors if `M > M0`.* It also doesn't seem to handle separate valence/conduction searches correctly with FEAST's interval approach.
        *   **Output:** Populates `upt%eigen_values`, `upt%eigen_vectors`.

### 4.7 Input/Output & File Handling

This section covers modules responsible for reading input parameter files and writing output data, including eigenvalues, eigenvectors, and visualization files.

#### 4.7.1 `savemofile.f90`

*   **Purpose:** Handles writing and reading of eigenvalue/eigenvector data to/from files, primarily a custom binary format (`states.data`) and various visualization formats (`.mo`, `.cube`, `.jvxl`).
*   **Key Subroutines/Functions:**
    *   `write_eigenstates(upt)`: Writes the calculated eigenvalues (`upt%eigen_values`) and eigenvectors (`upt%eigen_vectors`) to a binary file (`upt%state_file`). It iterates through valence and conduction bands, writing a record for each state containing particle type (+1 electron, -1 hole), the eigenvalue, and the full eigenvector array. Uses stream access for efficiency.
    *   `append_eigenstate(file_name, eigvec, eigval, particle)`: Appends a single eigenstate (particle type, eigenvalue, eigenvector) to the specified binary `file_name`. This allows iterative solvers like Lanczos to save states as they converge without holding all results in memory. Uses stream access and appends to the end.
    *   `read_eigenstates(upt, file_name, ev, ec)`: Reads eigenstates from the binary `file_name`. It allocates `upt%eigen_values`, `upt%eigen_vectors`, `upt%particles` if necessary. It reads records sequentially, filling the arrays until the end of the file or the allocated size is reached. It returns the number of valence (`ev`) and conduction (`ec`) states successfully read.
    *   `read_eigenvalues(upt, file_name, ev, ec)`: Reads *only* eigenvalues from an ASCII file (`file_name`, typically `eigv.dat`). This is used to quickly check which states might already be available (e.g., from a previous run) before deciding whether to load the full (potentially large) eigenvectors using `read_eigenstates`. It parses the header line to count existing valence (`ev`) and conduction (`ec`) states and reads the corresponding eigenvalues into `upt%eigen_values`. It sets `upt%start_vb` and `upt%start_cb` to indicate the next states to be calculated.
    *   `read_old_eigenstates(...)`: Reads eigenvectors from an older, likely deprecated, ASCII format.
    *   `write_eigenvalues(upt)`: Writes the calculated eigenvalues to an ASCII file (`eigv.dat`) in a formatted table, including a header indicating valence (Ev) and conduction (Ec) bands.
    *   `writemofile(upt)`: Writes data in the `.mo` ASCII format, suitable for visualization software like Molden. Includes header information, atom coordinates (converted to atomic units), basis set information (approximated as STOs with fixed exponents/coefficients), and the molecular orbital coefficients (eigenvector components).
    *   `write_cube(upt)`: Generates Gaussian Cube files (`.cube`) for visualizing the squared modulus (`|psi(r)|^2`) of selected molecular orbitals (eigenvectors).
        *   Calculates the grid dimensions (`Np`) and origin (`mincoord`) based on atomic coordinates and `upt%grid_step`.
        *   For each selected MO (`mo`):
            *   Calculates atomic contributions (`atomcharge`) using `getatomcharges`.
            *   Calculates the density `rho(i,j,k)` on the grid using `compute_rho`, which sums contributions from Slater-type orbitals centered on each atom, weighted by `atomcharge`.
            *   Determines isosurface cutoff values for visualization using `find_cutoff`.
            *   Writes the cube file header (comments, number of atoms, origin, grid vectors, atomic numbers/charges/coordinates) and the volumetric data `rho`.
    *   `write_jvxl(upt)`: Generates JVXL files, the native format for Jmol isosurfaces.
        *   Similar process to `write_cube` in calculating `rho`.
        *   Uses the Marching Cubes algorithm (`processOneCubical`) to generate surface triangulation data directly for a given `cutoff` value (determined by `find_cutoff` for a specified `fraction`).
        *   Encodes vertex positions along cube edges using a compact character representation (`jvxlFractionAsChar`).
        *   Writes the JVXL header (voxel counts, grid vectors, atom data, surface definition including cutoff and color encoding) followed by the encoded surface data (plane information and edge vertex data).
    *   `getNp`, `getatomcharges`, `compute_rho`, `find_cutoff`, `get_norm`, `get_partial`, `processOneCubical`, `jvxlFractionAsChar`, `atomZ`, `localization`: Helper functions specifically for `.cube` and `.jvxl` file generation, handling grid setup, density calculation, normalization, isosurface finding (Marching Cubes), and format-specific encoding.

#### 4.7.2 `input_data.f90`

*   **Purpose:** Reads the material parameter files (`.etb` or `.data`) which define the tight-binding model (onsite energies, couplings, etc.) for specific materials or parent components of alloys.
*   **Key Subroutines/Functions:**
    *   `read_data(mat_data, work_path, database_path)`: The main routine for reading parameters for a given `material_data` entry.
        *   **Inputs:** `mat_data` (TYPE(material_data)), `work_path`, `database_path`.
        *   **Action:** Loops through the parent materials defined in `mat_data%parent`. For each parent `i_par`:
            1.  Constructs the parameter filename using `mat_data%parent(i_par)%data_file`.
            2.  Searches for the file first in `work_path`, then in potentially multiple paths specified in `database_path` (colon-separated). Opens the file using `open_file`.
            3.  Reads header information using `label_in_file` and standard READ statements: `scheme`, `material type`, `basis type`, `reference axis`.
            4.  Reads `number of ions` (`n_ion`) and allocates `mat_data%parent(i_par)%ion`.
            5.  Reads `number of pairs` (`n_pair`) and allocates `mat_data%parent(i_par)%pair`.
            6.  Calls `read_ETB_orbitals` to read onsite and spin-orbit parameters for each ion.
            7.  Adds the material's valence band energy `e_v` to the read `offset` for each ion. *Note: The actual addition to onsite `energy` seems commented out here but might happen elsewhere.*
            8.  Calls `read_ETB_couplings` to read two-center parameters for each pair.
            9.  If the scheme is 'tan', calls `read_ETB_ons_corr` and `read_ETB_intra` to read Tan-specific correction parameters.
            10. Closes the parameter file.
        *   **Output:** Populates the `ion` and `pair` arrays within `mat_data%parent`.
    *   `read_ETB_orbitals(file_num, ion)`: Reads the `onsite` and `spin orbit` sections for each ion type within a parent material file.
        *   Reads `number of orbitals per ion` and `number of spin-orbit parameters per ion`.
        *   Reads ion names.
        *   For each ion: Reads valence, onsite data (orbital symbol, energy, degeneracy), offset, and `b_d` parameter. Reads spin-orbit data (orbital symbol, energy).
        *   Allocates and populates the `ion_orbit` structure (`ion(i_ion)`) passed as input, expanding degenerate orbitals using `states_sym`.
    *   `read_ETB_couplings(file_num, mat_data, i_parent, scheme)`: Reads the `coupling` section for each pair defined in the parent material file.
        *   For each pair: Reads pair names, number of couplings (`n_cpl`), and interaction order. Allocates arrays within `mat_data%parent(i_parent)%pair(i_pair)`.
        *   Reads coupling data line by line: coupling symbol, energy, scaling exponent. For Tan scheme, also reads `fac_P`, `fac_S`, `fac_Q`.
        *   Reads the reference distance `dist_ref`.
    *   `read_ETB_ons_corr(file_num, mat_data, i_parent)`: Reads Tan-scheme specific onsite correction parameters (`ons_corr`, `fac_I`, `l_I`), SO corrections (`so_corr`, `fac_so`), and offset corrections (`fac_O`, `l_O`, `delta_d`) for each pair.
    *   `read_ETB_intra(file_num, mat_data, i_parent)`: Reads Tan-scheme specific intra-atomic coupling parameters (`intra`, `fac_C`) for each pair.
    *   `states_sym(orb, n_states)`: Helper function used by `read_ETB_orbitals` to expand shorthand orbital names (like 'p', 'd') into their components ('px', 'py', 'pz', 'dxy', etc.) based on standard degeneracy rules. Returns a character array of state names.

### 4.8 Sparse Matrix Handling

This section details modules related to the definition, creation, manipulation, and conversion of sparse matrix formats used within Uptight.

#### 4.8.1 `sparse_matrix.f90`

*   **Purpose:** Defines various derived types for representing sparse matrices (CSR, COO, MSR, ELL, CSB) and provides core routines for creating, destroying, and converting between these formats.
*   **Key Derived Types:**
    *   `CSR_ex`: Modified Sparse Row (MSR) format, based on Numerical Recipes. Stores diagonal elements in `M(1:nrow)`, off-diagonal values in `M(nrow+2:...)`. `Mij(1:nrow+1)` stores pointers to the start of each row's off-diagonal elements in `M`/`Mij`. `Mij(nrow+2:...)` stores column indices for off-diagonal elements.
    *   `CSR`: Compressed Sparse Row format. `M` stores non-zero values, `Mj` stores corresponding column indices, `Mi` stores pointers (row starts) into `M`/`Mj`. `Mi(nrow+1)` points just beyond the last element.
    *   `CSR_real`, `CSR_real_sp_mx_prec`: Real-valued versions of CSR (double and single precision, respectively).
    *   `COO`: Coordinate list format. Stores triplets of (row index `Mi`, column index `Mj`, value `M`) for each non-zero element.
    *   `ELL`: ELLPACK format. Stores values (`M`) and column indices (`Mj`) in dense arrays where each row has a fixed width (maximum number of non-zeros per row). `rowsize` stores the actual number of non-zeros in each row. Potentially memory-inefficient but can be good for vectorization.
    *   `DNS`: Dense matrix type (`val(:,:)`). Used as blocks within `CSB`.
    *   `CSB`: Compressed Sparse Block format. Represents the matrix as a collection of smaller dense blocks. `Row(i)%B(j)` accesses the j-th block in the i-th block-row. `Row(i)%col(j)` gives the block-column index corresponding to block `B(j)`.
*   **Key Subroutines/Functions (Interfaces):**
    *   `create_matrix`: Allocates memory for the specified sparse matrix type (`CSR`, `CSR_real`, `CSR_real_sp_mx_prec`, `COO`, `CSB`, `DNS`). Takes dimensions (`nrow`, `ncol`) and estimated non-zeros (`nnz`) or block structure (`nbl`, `szbl`) as input.
    *   `destroy_matrix`: Deallocates memory associated with the specified sparse matrix type. Handles nested deallocation for `CSB`.
    *   `get_nrow`: Returns the number of rows (`nrow`) for `CSR_ex` or `CSR` types.
    *   `get_nnz`: Returns the number of non-zero elements (`nnz`) for `CSR_ex` or `CSR` types.
    *   `read_coo`: Reads a matrix from a file in Coordinate List (COO) format.
*   **Key Subroutines/Functions (Specific):**
    *   `sprs_to_csr(M, Mij, A, JA, IA)`: Converts MSR format (`M`, `Mij`) to CSR format (`A`, `JA`, `IA`).
    *   `sprs_to_coo(M, Mij, A, JA, IA)`: Converts MSR format (`M`, `Mij`) to COO format (`A`, `JA`, `IA`).
    *   `coo_to_csr(M_in, M_out)`: Converts COO (`M_in`) to CSR (`M_out`). Requires `M_out` arrays to be pre-allocated. Uses a two-pass approach (first counts row lengths, then fills).
    *   `csb_to_csr(M, A, cutoff)`: Converts CSB (`M`) to CSR (`A`). Iterates through blocks, copying elements `val` where `abs(val) > cutoff`. Requires `A` to be pre-allocated with sufficient size (calculated beforehand).
    *   `csr_to_coo(M_in, M_out)`: Converts CSR (`M_in`) to COO (`M_out`). Requires `M_out` arrays to be pre-allocated.
    *   `write_sprs_to_coo(...)`, `write_csr_to_coo(...)`: Convenience routines to write MSR or CSR matrices to file in COO format (suitable for MATLAB).
    *   `write_coo(...)`, `write_csr(...)`: Write COO (ASCII for MATLAB) or CSR (binary stream) formats to file.
    *   `analyze(ham)`: Prints statistics about a CSR matrix (number of non-zeros, min/max/average row length, distribution of row lengths).
    *   `drop(A)`, `zcheck_nnz(A, ...)`: Routines to remove explicit zero entries from a real CSR matrix (`CSR_real`). `zcheck_nnz` counts non-zeros (potentially within a submatrix), `drop` creates a new matrix `B` containing only non-zeros, destroys `A`, and reallocates `A` with the contents of `B`.
    *   `drop_sp_mx_prec(A)`, `zcheck_nnz_sp_mx_prec(A, ...)`: Single-precision versions of `drop` and `zcheck_nnz` for `CSR_real_sp_mx_prec` type.
    *   `split_matrix(H, H_real, H_imag)`: Splits a complex CSR matrix `H` into two real CSR matrices `H_real` and `H_imag`, containing the real and imaginary parts, respectively. Calls `drop` on `H_imag` to remove zero entries resulting from real diagonal elements.
    *   `split_matrix_sp_mx_prec(...)`: Single-precision version of `split_matrix`.

#### 4.8.2 `sparse_numrec.F90`

*   **Purpose:** Contains utility routines for operating on sparse matrices, primarily focusing on the MSR (`CSR_ex`) format but also providing interfaces for CSR. Includes matrix-vector products, element access/modification, shifting, testing, and wrappers for external libraries (SPARSKIT). Handles MPI parallelism for some operations.
*   **Key Subroutines/Functions (Interfaces):**
    *   `sprs_matrix`: Reads matrix from file. `sprs_matrix_ex` reads into MSR, `sprs_matrix_csr` reads into CSR.
    *   `sprs_element`: Gets element `(row, col)`. `sprs_element_ex` (MSR) searches linearly within the row's off-diagonal entries. `sprs_element_csr` (CSR) uses binary search within the row.
    *   `set_sprs_element`: Sets element `(row, col)` to `val`. Implementations `set_sprs_element_ex` (MSR) and `set_sprs_element_csr` (CSR) use similar search logic as `sprs_element`. *Warning: Modifying sparse matrices after construction can be inefficient.*
    *   `sprs_shift`: Adds `shift` to diagonal elements. `sprs_shift_ex` adds to `M(1:nrow)`. `sprs_shift_csr` and `sprs_shift_csr_real` find the diagonal element within each row's CSR data and add the shift. Includes MPI parallelization hints (`shift_init`, `shift_end`).
    *   `sprs_ax`: Computes `ax = Matrix * x`.
        *   `sprs_ax_ex` (MSR): Handles 'U'/'L' (symmetric) or 'F' (full) formats. Symmetric versions compute `M(i,i)*x(i)` and sum contributions `M(i,j)*x(j)` and `M(j,i)*x(i)` (using `conjg(M(k))` for the lower part). Full version uses standard row-based multiplication with OpenMP parallelization.
        *   `sprs_ax_csr` (CSR): Similar logic for 'U'/'L' and 'F' formats using CSR indexing. OpenMP parallelization for 'F'. Includes MPI communication (`exchange_vector`) for halo regions.
        *   `sprs_ax_csr_real` (CSR Real): Real version of `sprs_ax_csr`.
    *   `test_eigvect`: Computes Rayleigh quotient `<x|H|x> / <x|x>`. Calls `sprs_ax` and then computes dot products. Includes MPI reduction (`mpi_allreduce`) for parallel execution. Implementations for MSR (`test_eigvect_ex`), CSR (`test_eigvect_csr`), and real CSR (`test_eigvect_csr_real`).
    *   `premult`, `mult`: Interfaces likely intended for matrix-matrix multiplication, wrapping SPARSKIT's `zamub`.
    *   `reorder`: Reorders a CSR matrix in-place using RCM permutation (`genrcm`) and SPARSKIT routines (`zamub`, `ztransp`).
*   **Other Routines:**
    *   `compute_ovr(M, colind, rowpnt, col_ind_low, col_ind_hig)`: Determines the minimum (`col_ind_low`) and maximum (`col_ind_hig`) column index accessed by rows within the current MPI process's range (`shift_init` to `shift_end`). Used to define communication halo regions.
    *   SPARSKIT wrappers (`zmsrcsr`, `zcsrcsc2`, `zaplb`, `zcsrmsr`, `ztransp`, `iperm`, `zperm`, `zamub`): Low-level routines from the SPARSKIT library used for format conversions (MSR<->CSR, CSR<->CSC), matrix addition (`zaplb`), and matrix multiplication (`zamub`).

#### 4.8.3 `sparse_matrix_rout.f90`

*   **Purpose:** Contains older routines for manipulating the MSR (`CSR_ex`) sparse matrix format, likely superseded by routines in `sparse_numrec.F90` or `sparse_matrix.f90`.
*   **Key Subroutines/Functions:**
    *   `setup_sparse_matrix`: Allocates MSR arrays (`sa`, `ija`).
    *   `add_element_sparse`: Adds an element to the MSR structure, shifting existing elements as needed (inefficient). Assumes only upper triangle + diagonal is added.
    *   `check_sparse_matrix`: Performs consistency checks on the MSR structure (likely only valid if `max_offdiag` equals actual non-zeros).
    *   `add_element_sparse_restr`: A restricted version of `add_element_sparse` that avoids some shifting but might have stricter usage conditions.
    *   `matvec_sparse`: Computes `bV = Matrix * xV` for MSR format, explicitly handling symmetry.
    *   `matTvec_sparse`: Computes `bV = Matrix^T * xV` for MSR format.
    *   `deallocate_sparse_matrix`: Deallocates MSR arrays.
    *   `num_rec_v_sp_m`, `num_rec_v_sp_m_upper`: Convert a dense matrix `a` to MSR format, storing elements >= `thresh`.

### 4.9 Main Interface & Examples

This section describes the main high-level Fortran interface provided by the library and the example programs demonstrating its usage.

#### 4.9.1 `uptight.F90` (Module `UPTIGHT`)

*   **Purpose:** Provides a high-level Fortran interface module, wrapping the core functionalities like initialization, Hamiltonian construction, diagonalization, and destruction into convenient subroutines operating on the `OUPT` type. This is the intended primary entry point for using Uptight as a library in other Fortran codes.
*   **Key Subroutines/Functions:**
    *   `UPT_init(upt)`: Initializes the `OUPT` structure and all underlying data structures by calling relevant routines from other modules (e.g., `init_structure`, `make_basis`, `read_data`, `ref_states_and_couplings`, `init_mat_ion`, `init_basis`, `refine_neighbours_map`, `subs_dg_ions`, `init_n_st`). Handles MPI initialization (`upt_mpi_init`).
    *   `UPT_destruct(upt)`: Deallocates all memory associated with the `OUPT` structure and its members by calling the respective `destroy_*` routines. Calls `upt_mpi_end`.
    *   `UPT_hamiltonian(upt)`: Constructs the sparse Hamiltonian matrix (`upt%ham`) by calling `sparse_ham`. Includes checks for previously allocated matrices.
    *   `UPT_lanczos(upt)`, `UPT_jd(upt)`, `UPT_lapack(upt)`, `UPT_feast(upt)`: Call the respective solver driver routines (`lanczos`, `jd`, `lapack`, `feast`) to diagonalize the Hamiltonian stored in `upt%ham`.
    *   `UPT_write_eigenvectors(upt)`: Calls routines from `savemofile` (e.g., `write_cube`, `write_jvxl`) to write visualization files based on the calculated eigenvectors stored in `upt`.
    *   `UPT_get_mat_el(upt, i, j, matel)`: Calculates and returns the matrix element `<psi_i|H|psi_j>` where `psi_i` and `psi_j` are eigenvectors stored in `upt%eigen_vectors`. It computes `H|psi_i>` using `sprs_ax` and then takes the dot product with `<psi_j|`. Includes MPI reduction for parallel execution.
    *   `UPT_nullify_all(upt)`: Nullifies all pointer members within the `OUPT` structure to prevent dangling pointers.
    *   `UPT_set_defaults(upt)`: Initializes an `OUPT` variable with default parameter values by calling `set_defaults` from the `upt_param` module.
    *   `UPT_get_hamil(upt, nrow, ncol, fmt, M, Mj, Mi)`: Provides pointer access (`M`, `Mj`, `Mi`) to the internal CSR representation of the Hamiltonian stored in `upt%ham`. Also returns dimensions (`nrow`, `ncol`) and format (`fmt`).
    *   `UPT_version(upt)`: Prints version information (revision, date, modification) embedded during compilation via preprocessor flags set in the Makefile.
    *   `UPT_alloc_eigv(upt)`: Allocates space for `upt%eigen_values`, `upt%eigen_vectors`, and `upt%particles` based on `upt%num_vb`, `upt%num_cb`, and `upt%ham%nrow`. Checks if arrays are already associated.
    *   `UPT_writehamiltonian(upt)`: Writes the Hamiltonian matrix stored in `upt%ham` to files (`Hr.m`, `Hi.m`) in COO format suitable for MATLAB, using `write_csr_to_coo`.

#### 4.9.2 `parameterizer.f90` (Example Program)

*   **Purpose:** Serves as an example program demonstrating a typical workflow for using the `UPTIGHT` module to perform band structure calculations along a specified k-path. Based on its name, it might also contain or be intended for code related to fitting or adjusting tight-binding parameters against reference data, although the current implementation primarily focuses on band structure calculation. It reads control parameters, geometry, material data, k-points, calls the initialization, Hamiltonian construction, and diagonalization routines, and writes the results.
*   **Workflow:**
    1.  **Initialization:**
        *   Initialize MPI (`upt_mpi_init`).
        *   Read basic parameters from standard input (or a redirected file like `dr_bands`): `database_path`, `gen_filename`, `scaling` flag, `c_axis`.
        *   Set other `upt` parameters (filenames, verbosity, flags).
        *   Call `UPT_init(upt)` to set up the structure and parameters.
    2.  **Read Calculation Settings:**
        *   Read solver choice (`calc` string, e.g., 'LK' for LAPACK, 'LO' for Lanczos).
        *   Read k-point (`upt%k_point` - likely just the Gamma point for this specific example, k-path is read later).
        *   Read number of valence/conduction bands (`upt%num_vb`, `upt%num_cb`).
        *   Read energy guesses (`upt%lambda_vb`, `upt%lambda_cb`).
        *   Read k-point filename (`kfile`).
        *   Read uniform strain components (`strain`) and apply them to `upt%basis%strain`.
        *   Read flag (`coef2_cal`) and number of AO types (`n_ao_type`) for calculating orbital projections.
    3.  **Open Output Files:** Open `eigv.dat` and `coef2.dat` for writing results. Write headers.
    4.  **K-Point Loop:**
        *   Read k-points (`upt%k_point`) sequentially from the file specified by `kfile`.
        *   Call `UPT_hamiltonian(upt)` to construct the Hamiltonian `H(k)`.
        *   Allocate space for results using `UPT_alloc_eigv(upt)`.
        *   Call the selected solver (e.g., `call UPT_lapack(upt)` if `calc == 'LK'`).
        *   Calculate the distance along the k-path (`Lk`) relative to the first k-point.
        *   Write `Lk` and eigenvalues (`upt%eigen_values`) to `eigv.dat`.
        *   If `coef2_cal` is true:
            *   Transpose eigenvectors (`temp_eivec = transpose(upt%eigen_vectors)`).
            *   Call `AO_decomposition(temp_eivec(i,:), coef2, ...)` for each state `i` to get orbital projections.
            *   Write `Lk`, eigenvalue, and `coef2` values to `coef2.dat`.
        *   Deallocate eigenvalue/vector arrays for the current k-point.
    5.  **Cleanup:** Close output files, call `UPT_destruct(upt)`, finalize MPI (`upt_mpi_end`).
*   **`AO_decomposition(...)`:** Calculates the squared modulus contribution of each orbital type (s, p, d, potentially f depending on `n_ao_type`) for each atom to the input eigenvector `eivec`.

## 5. Parameterization

Uptight uses text files to define the tight-binding model parameters and the atomic structure for calculations. These are primarily found in the `parameters/` and `bulk/` directories.

*   **`parameters/` Directory:**
    *   Contains subdirectories corresponding to different published or developed parameter sets (e.g., `Jancu`, `Tan`, `sp3`, `sp3s`).
    *   These subdirectories typically contain `.etb` files (e.g., `parameters/sp3s/GaAs.etb`).
    *   `.etb` files define the electronic parameters (onsite energies, couplings, spin-orbit) for a specific material within a given model (like sp3s*).
    *   **`parameters/states.info`:** Defines the standard ordering and naming convention for atomic orbitals (s, px, py, pz, s*, dxy, etc.) and coupling types (sss, sps, pss, etc.) used throughout the code and parameter files.

*   **`bulk/` Directory:**
    *   Contains input files, primarily with the `.data` extension (e.g., `bulk/GaAs.data`, `bulk/Si.data`).
    *   These files often define parameters for specific bulk materials or variations (e.g., strained materials, alloys).
    *   `.data` files typically contain **both** structural information (lattice type, constants, basis type) and a complete set of tight-binding parameters (onsite, couplings, spin-orbit), similar to `.etb` files. They essentially define a specific calculation setup for a bulk material.
    *   Some `.etb` files are also present here, possibly duplicates or specific overrides.

*   **File Format (`.etb` / `.data`):**
    *   Text-based, keyword-driven format. Comments start with `#`. Values are typically assigned using `=`.
    *   **Keywords and Expected Values:**
        *   `scheme = '<scheme_name>'`: (Optional) Specifies parameterization scheme. `<scheme_name>` is typically `'jancu'` (default) or `'tan'`.
        *   `material type = '<type>'`: Material composition. `<type>` is `'simple'`, `'binary'`, `'ternary'`, or `'quaternary'`.
        *   `lattice type = '<type>'`: Lattice symmetry. `<type>` is `'face centered cubic'` or `'hexagonal'`.
        *   `lattice parameters = <val1> <val2> <val3>`: Lattice constants (a, b, c) in Angstroms. Values are REAL(dp).
        *   `internal strain parameter = <value>`: Internal strain parameter (e.g., for WZ relaxation). Value is REAL(dp).
        *   `basis type = '<type>'`: Basis arrangement. `<type>` is `'zinc-blende'` or `'wurtzite'`.
        *   `reference axis = <x> <y> <z>`: (Optional) Reference crystallographic axis used for parameterization. Values are REAL(dp). Defaults depend on `basis type`.
        *   `number of ions = <N>`: Number of distinct ion types. `<N>` is INTEGER.
        *   `ions = '<Ion1>' '<Ion2>' ...`: List of ion type names (CHARACTER). Must match `number of ions`.
        *   `<IonName> valence = <V>`: Valence electrons for `<IonName>`. `<V>` is INTEGER. (Repeated for each ion).
        *   `number of spin-orbit parameters per ion = <N1> <N2> ...`: Number of SO parameters for each ion type. Sequence of INTEGERS.
        *   `<IonName> spin orbit`: Section header. Followed by `N` lines of:
            *   `'<orbital_char>' <SO_Energy>`: Orbital type ('p' or 'd') and SO energy (REAL(dp)).
        *   `number of orbitals per ion = <N1> <N2> ...`: Number of distinct orbital energy entries for each ion type. Sequence of INTEGERS.
        *   `<IonName> onsite`: Section header. Followed by `N` lines of:
            *   `'<orbital_symbol>' <Onsite_Energy> <Degeneracy>`: Orbital symbol ('s', 'p', 'd', 's*', 'px', 'dxy', etc.), onsite energy (REAL(dp)), and degeneracy (INTEGER).
        *   `<IonName> offset = <value>`: Energy offset for this ion type (REAL(dp)).
        *   `<IonName> b_d parameter = <value>`: Parameter for d-orbital strain effects (Jancu scheme) (REAL(dp)).
        *   `number of pairs = <N>`: Number of distinct interacting pairs defined. `<N>` is INTEGER.
        *   `pair <i> = '<IonA>' '<IonB>' <Num_Couplings> <Order>`: Header for the i-th pair, specifying names, number of coupling terms, and interaction order (INTEGER).
        *   `<IonA> <IonB> coupling <Order>`: Section header for coupling values. Followed by `<Num_Couplings>` lines:
            *   `'<coupling_symbol>' <Energy> <Scaling> [<P> <S> <Q>]`: Coupling type ('sss', 'sps', etc.), energy (REAL(dp)), scaling exponent (REAL(dp)). Optional P, S, Q factors (REAL(dp)) are read only for 'tan' scheme.
        *   `<IonA> <IonB> pair reference distance <Order> = <value>`: Reference bond distance for this interaction order (REAL(dp)).
        *   **(Tan Scheme Specific)** Additional sections like `onsite correction`, `SO correction`, `offset correction`, `intra` follow a similar pattern: Header defining the pair and number of terms, followed by lines with specific parameter names and values. Refer to `input_data.f90` (`read_ETB_ons_corr`, `read_ETB_intra`) for exact keywords and expected values.

## 6. Testing

The `TEST/` directory contains various test cases to verify the functionality of the Uptight library and associated tools.

*   **Structure:**
    *   Tests are organized into subdirectories, typically named after the material system and structure being tested (e.g., `TEST/GaAs/` for bulk Gallium Arsenide, `TEST/GaN_slab/` for a Gallium Nitride slab).
*   **Contents of Test Directories:**
    *   **Input Files:** Define the parameters and settings for a specific calculation. Common examples include:
        *   `data_driver_*`: Main driver file specifying the calculation type and parameters.
        *   `*.dat`, `*.xyz`, `*.input`: Atomic coordinates, basis information, structural details.
        *   `k_points.in`: Specifies k-points for band structure calculations.
        *   `state.dat`: Defines electronic states or parameters.
    *   **Output Files:** Files generated during or after a test run. Examples include:
        *   `*.log`, `output`, `fort.99`: Log files containing runtime information and results.
        *   `*_eigv.dat`, `*_vec.dat`: Calculated eigenvalues and eigenvectors.
        *   `H.dat`, `H_CSR.DAT`: Saved Hamiltonian matrix.
    *   **Scripts:** Some directories contain scripts (`*.script`, e.g., `gan.script`) which may automate the execution of the test case.
    *   **Verification/Analysis:** Files like `readmat.m` (MATLAB script) suggest that verification might involve post-processing or comparing results using external tools.
*   **Running Tests:**
    *   There does not appear to be a centralized test runner (e.g., `make check`).
    *   Tests are likely run individually by navigating into the specific test directory (e.g., `cd TEST/GaAs/`).
    *   Execution probably involves running an Uptight executable (like `PARAMETERIZER` or a custom program linked with `uptight.a`) with the appropriate input files, potentially guided by a local script (`*.script`).
    *   Verification involves examining the output files and possibly comparing them against known reference results or using analysis scripts.
*   **Adding Tests:**
    *   Create a new subdirectory within `TEST/`.
    *   Add the necessary input files (`data_driver_*`, structure files, parameter files, etc.).
    *   Include reference output files or a script for verification if possible.
